BILTIQ-010 — Operations Runbook

Feature: Audit Hash-Chain (Pure Logic)
Audience: Operations / Infrastructure

Overview

The BILTIQ-010 module provides a stateless, tamper-evident audit mechanism located in biltiq_privacy.core.audit_chain. Unlike legacy implementations tied to SQLAlchemy, this is a "leaf" library containing pure mathematical logic to ensure cryptographic integrity of audit logs across disparate systems (Postgres, S3, JSON files).

Core Logic:

  • append_row(prev_hash, payload): Computes a new ChainedRow using SHA-256.
  • verify_chain(rows): A single-pass forward walk that detects payload mutation, hash corruption, reordering, insertion, or deletion.
  • Genesis Anchor: All chains must anchor to GENESIS_PREV_HASH (64 zero-hex characters).

Compliance Note: Designed to satisfy 21 CFR Part 11 and Annex 11 requirements for data integrity and non-repudiation of audit trails.

Deployment

As a pure Python library, deployment is managed via standard package workflows. No database migrations or infrastructure provisioning are required for this specific component.

  • Integration: Consumers (e.g., CDSCO, CommandCenter) must import biltiq_privacy.core.audit_chain and integrate the append_row result into their existing persistence layer.
  • Dependency Check: Ensure requires-python >= 3.11. This module uses TypeAlias and the | union operator which are incompatible with older versions.
  • Verification: Post-deployment, run the existing test suite to ensure the doc_hasher SHA-256 primitive is correctly mapped to the new chaining logic.

Configuration

There are no runtime environment variables or config files for this module. Configuration is strictly defined by the Canonical Serialization Contract (ADR-0005):

json.dumps(payload, sort_keys=True, separators=(",", ":"), ensure_ascii=False)

Operational Constraints:

  1. Timestamps: The library does not read the system clock. Consumers must supply the timestamp within the payload to maintain determinism.
  2. Hashing: Uses the internal doc_hasher.hash_text. Do not replace this with hashlib.sha256().hexdigest() directly in consumer code to avoid divergence.

Rollback and Recovery

Because this is a stateless logic library, "rollback" refers to the library versioning in the application environment.

  • Rollback Strategy: In the event of a verification mismatch caused by a logic change, revert the Python package version to the previous stable release.
  • Data Recovery: If an audit chain is detected as "broken" (via verify_chain), the module will report the first_broken_index. Operations must investigate the storage layer at that specific index to determine if a hardware failure or malicious tampering occurred. Note: This module cannot "repair" a broken chain; it only detects the breach.

Monitoring and Alerts

Monitoring should be implemented at the Consumer Level (the service writing/reading the rows).

Alert Trigger Severity Action Required
verify_chain(rows).valid == False CRITICAL Immediate forensic audit of the storage layer. Possible data tampering or corruption.
TypeError during append_row WARNING Check consumer payload for non-JSON-serializable types (e.g., complex objects, datetimes instead of strings).
Missing GENESIS_PREV_HASH link HIGH Verify the integrity of the chain's origin; ensure the first row correctly references the 64-zero sentinel.
