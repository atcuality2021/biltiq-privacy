1. What went well

  • Golden-digest characterization caught the determinism contract cheaply. Computing the SHA-256/HMAC golden values externally (one throwaway python snippet) and hardcoding them — rather than recomputing with hashlib inside the test — turned AC3/AC5 into a true behaviour gate instead of a tautology. The same [PERSON_8ec2c852] token reproduced in Build, Test, and the live AC demo, which is the auditability property the module exists to provide.
  • The design's "Alternatives Considered" table pre-empted a real wrong turn. Alt #1 (per-call key) and Alt #4 (lazy raise) were both tempting and both would have failed AC4's "before any text is processed" boundary. Having them rejected in writing meant Build never relitigated constructor-time validation.
  • Static source-assertion test (test_no_settings_or_env_import) is the right shape for a compliance invariant. It pins the one rule that defines this module's on_prem_preferred posture (no env key-read in python-core) against future refactors a behavioural test would miss. The Test step's runtime "no env read: True" echo is defense-in-depth on the same line.
  • Decouple-don't-rewrite kept the diff small and the risk low. Three modules, ~185 LOC source, stdlib-only, no ADR, no new dependency — and every CDSCO behaviour (token form, end→start replacement, audit reversal, 5 keys) preserved verbatim.

2. What went wrong (caught in Review/Test)

  • Anti-Pattern #6 (scope creep) — narrowly avoided at Build, not Review. I created tests/core/test_public_imports.py, a file the plan named only by test-name and that design.html § Files-to-touch did not list. The plan-reviewer's reverse-coverage gate (TD-M28-08) would have flagged it at Review. I caught it during Build self-review and amended both design.html and plan.html before committing Step 4 — the cheap fix (one edit) versus a Review round-trip.
  • Plan/branch drift. plan.html declared the build branch as feature/biltiq-007-core-pseudonymiser off main, but the approved spec/design/plan lived on feature/biltiq-phase-a-core. Building on the named branch would have produced an artifact-less branch. Reconciled the plan header to the real branch and logged it in change-history; surfaced to the dev at Ship, who chose to fold into PR #9.

3. What we missed (slipped past Review & Test, caught later)

  • Tooling drift between branches — caught at Ship/Reflect, not earlier. Two ship/reflect gate scripts named by the skills — scripts/_product_docs.py (M34 product-doc ship gate) and scripts/_flip_ac_badges.py (AC badge flip) — and _memory_writer.append_estimate_actual do not exist on feature/biltiq-phase-a-core (it branches from main; those land on the in-flight BILTIQ-006 memory-spine branch). The M34 gate degraded to allow-with-warning (recorded in the PR), the badge flip was done manually, and the estimate actual was recorded in prose here rather than appended to .biltiq/estimates-history.jsonl. Nothing blocked, but the workflow assumed scripts the working branch doesn't carry.
  • CI parity was unverified locally until Ship. The 4-version matrix (py3.11→3.14) is what actually proves the bytes | str union + golden-digest determinism across the support window; locally I only ran the repo venv. It passed 9/9, but "green on my interpreter" was an assumption until CI confirmed it.

4. Process changes proposed

  • Ship/Reflect skills should tolerate absent gate scripts explicitly. The M34 ship gate already has an allow-with-warning fallback for "vLLM unreachable" but not for "_product_docs.py not on this branch." Propose: the skill text should treat a missing gate script the same as the unreachable-vLLM case (warn, don't block) — which is what I did, but it should be documented rather than improvised. Pending Friday review.
  • Plan template should derive the build branch, not hardcode a sibling. The "Branch" header in plan.html defaulted to a per-task branch that didn't match the phase branch the artifacts lived on. Propose: when a task ships inside a phase branch, the plan's Branch field should reference the phase branch (or the plan-reviewer should warn on a Branch value that doesn't yet exist).
  • No AGENT_RULES.md change proposed — the anti-patterns and compliance rules all held.
