Problem

biltiq_privacy/core/ is an empty package stub. The deterministic HMAC pseudonymisation logic the engine needs already exists in CDSCO-RegAI (backend/utils/doc_hasher.py, backend/modules/anonymisation/pseudonymiser.py) but is coupled to that app: doc_hasher reads settings.HMAC_KEY from a global config object. To productise the engine as a standalone, leaf-of-tree library, this logic must be ported with the key injected as a constructor argument — never read from the environment inside python-core (a forbidden placement per overview.md).

User Impact

Internal/infra. Establishes the first real core/ module: consumers get deterministic, reversible-by-key-holder pseudonymisation with an explicit, auditable key-handling contract. Unblocks BILTIQ-012 (orchestration) and BILTIQ-011 (DPDP token-reversibility check).

Acceptance Criteria

  • OPENAC1 — core/doc_hasher.py exposes hash_document(file_bytes: bytes) -> str, hash_text(text: str) -> str (SHA-256), and hmac_pseudonymise(value: str, *, key: bytes|str) -> str (HMAC-SHA256). The HMAC key is a parameter; no settings/env/config import anywhere in the module.
  • OPENAC2 — core/pseudonymiser.py exposes make_token(entity_type, value, *, token_length=8) -> str producing a stable [TYPE_<hex>] token (default 8 hex = CDSCO-equivalent; token_length configurable), and pseudonymise_text(text, detections) -> tuple[str, list[dict]] returning (anonymised_text, audit_list).
  • OPENAC3 — Determinism: identical (value, entity_type, key) yields an identical token across processes; a different key yields a different token. Pinned by test.
  • OPENAC4 — Missing key fails fast: constructing/using the pseudonymiser without a key raises HMACKeyRequiredError before any text is processed (per overview.md failure modes).
  • OPENAC5 — Characterization tests port CDSCO behaviour: token format, determinism, multi-entity replacement, audit-list shape. No Any/# type: ignore without justification; passes --strict.

Out of Scope

  • PII detection (BILTIQ-009) and generalisation (BILTIQ-008).
  • A reversible-token vault / re-identification store — pseudonymisation here is forward-only; reversal is the key-holder's concern.
  • Regime checks that consume the audit list (BILTIQ-011).

Open Questions

  • RESOLVED (2026-06-01): Key type — accept bytes, with str convenience (utf-8-encoded internally). Always a constructor/call argument; never read from env in python-core.
  • RESOLVED (2026-06-01): Token digest length — token_length parameter, default 8 (CDSCO-equivalent). Configurable so consumers at larger scale can widen collision resistance.
