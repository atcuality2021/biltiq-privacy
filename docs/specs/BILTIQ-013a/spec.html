Problem

The BILTIQ-013 sidecar is verify-only: it checks Authorization: Bearer <token> against BILTIQ_JWT_SECRET but never issues tokens (ADR-0007; auth.py calls only jwt.decode). Token minting is "the consumer's concern" — which is correct for production clients that mint their own JWTs, but leaves an operator with no first-class way to produce a token for a smoke test, a curl against a fresh deployment, or a local integration run. Today the only path is the PyJWT snippet pasted in the README, which is easy to get wrong (naive exp, tz-naive timestamps, wrong algorithm) and tempts operators to put the signing secret on the command line.

This task adds a small, standalone operator helper that mints a correct short-lived HS256 token — without weakening the verify-only guarantee of the running server.

User Impact

Operator-facing, on-prem. BILTIQ_JWT_SECRET=… biltiq-privacy-mint --sub ops --ttl 3600 prints a ready-to-use bearer token to stdout. Pipe-friendly: TOKEN=$(BILTIQ_JWT_SECRET=… biltiq-privacy-mint --sub ops). The minted token verifies against the same server unchanged. No production client is required to use it — it is a convenience for operators and CI smoke tests, not a new auth surface on the server.

Design Constraints (ruling before design)

  • Verify-only runtime is preserved. The ASGI import graph (biltiq_privacy_server.app:app → routers → dependencies → auth) must never reach jwt.encode. The minting code lives in a dedicated module reachable only via its own console-script, never imported by the app. This is the invariant the parent task was built on; it is amended, not broken — see ADR-0007.
  • Secret is env-only. The signing secret is read from BILTIQ_JWT_SECRET (the same env var the server verifies against). It is never accepted as a CLI argument — a signing key in argv leaks into ps, shell history, and process listings.
  • HS256 only. The mint signs with HS256 to match the verify side's pinned single-element allow-list (auth._ALGORITHMS). No algorithm flag.
  • Claim shape matches the verify side. Minted payloads carry tz-aware iat/exp (datetime.now(UTC)) and the operator-supplied sub — the same shape tests/conftest.py::_mint_token already uses, so tokens verify unchanged.
  • No new dependency. PyJWT is already a server dependency; the CLI uses stdlib argparse like cli.py (keeps the air-gapped install path clean).
  • No coupling to load_settings(). Minting needs only the JWT secret; it must not require BILTIQ_HMAC_KEY (which load_settings() mandates). The mint reads BILTIQ_JWT_SECRET directly via the shared env-var constant.

CLI Contract (informational — design finalises)

BILTIQ_JWT_SECRET=<secret> biltiq-privacy-mint \
    --sub ops \                 # required: token subject
    --ttl 3600 \                # optional: lifetime in seconds (default 3600)
    --claim role=admin \        # optional, repeatable: extra string claims
    --claim team=privacy

→ stdout: <the.jwt.token>        # token ONLY, newline-terminated, pipe-friendly
→ exit 0

# error paths (token never printed):
BILTIQ_JWT_SECRET unset/empty      → stderr "BILTIQ_JWT_SECRET is required …", exit != 0
--claim with no '='                → stderr "malformed --claim …", exit != 0
--claim sub=… / iat=… / exp=…       → stderr "reserved claim …", exit != 0

Acceptance Criteria

HIGH-RISK ticket (token-signing path). Amends ADR-0007. Mandatory human plan review before Step 3 Build and mandatory human code review before merge. Skill review does not substitute.
  • DONEAC1 — mints a verifiable token. With BILTIQ_JWT_SECRET set, biltiq-privacy-mint --sub ops prints a single HS256 JWT to stdout (token only, newline-terminated, nothing else on stdout) that auth.verify_token(token, secret=<same secret>) accepts, returning claims whose sub == "ops".
  • DONEAC2 — secret is env-only. The signing secret is read from BILTIQ_JWT_SECRET via the shared env-var constant. The parser exposes no --secret (or equivalent) flag — asserted by a test that inspects the argparse actions. The secret never appears in stdout.
  • DONEAC3 — fail-fast on missing secret. With BILTIQ_JWT_SECRET unset or empty, the CLI writes an actionable message to stderr, exits non-zero, prints nothing to stdout, and never echoes any secret value.
  • DONEAC4 — sub + ttl, tz-aware. --sub is required and sets the sub claim. --ttl (seconds, default 3600) sets exp = iat + ttl; both iat and exp are timezone-aware UTC (datetime.now(UTC)) — satisfies ruff DTZ. A non-positive --ttl is rejected (stderr, non-zero exit).
  • DONEAC5 — extensible claims. --claim k=v is repeatable; each pair is merged into the payload as a string value. A --claim without = is rejected (stderr, non-zero). A --claim naming a reserved claim (sub, iat, exp) is rejected — those are set by --sub/--ttl/the clock, not free-form. Extra claims are minted verbatim and not enforced by the current verify-only server (no roles model yet).
  • DONEAC6 — verify-only invariant preserved. A structural test imports the full biltiq_privacy_server.app:app graph and asserts no module in that graph references jwt.encode; jwt.encode lives only in the dedicated mint module (and tests). The mint module is not imported by app, auth, dependencies, or any router.
  • DONEAC7 — packaging + docs. pyproject.toml registers the biltiq-privacy-mint console-script. ADR-0007 is amended to record the operator-mint carve-out; approved-versions.md's "production never calls jwt.encode / auth.py is the only importer" row is updated to "the request-handling runtime never calls encode; the operator mint tool does, in a module the app never imports." README documents the command.
  • DONEAC8 — gates green. pytest green, mypy --strict clean (no Any, no unjustified type: ignore), ruff check clean, deprecation-warning-free, coverage ≥ 90% on the new module.

Out of Scope

  • Roles/authorization enforcement. The server stays verify-only with binary access (valid token / 401). --claim role=… mints the claim but nothing reads it server-side. A roles model is a separate future ticket.
  • JSON-typed claim values. --claim values are strings in v1. Typed/nested claim values (numbers, booleans, JSON) are deferred.
  • Token revocation / introspection / refresh. No server-side token store; revocation is out of scope (rotate BILTIQ_JWT_SECRET to invalidate).
  • Asymmetric (RS/ES) signing. HS256 only, matching the verify side.
  • A serve-CLI subcommand. Mint is a separate console-script, not a subcommand of biltiq-privacy-server — that placement would put encode into the server CLI's import surface.
