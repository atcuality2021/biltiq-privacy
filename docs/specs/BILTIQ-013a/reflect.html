Outcome

Shipped biltiq-privacy-mint, a standalone operator/CI console-script (biltiq_privacy_server.mint:main) that signs a short-lived HS256 bearer token the verify-only sidecar accepts — so operators stop hand-rolling the PyJWT snippet (and stop being tempted to put the signing key on the command line). 2 atomic build steps, one commit each (code + tests + docs per step). Final battery: 22 mint tests, mint.py 100% coverage (12/12 branch), full server suite 90 passed (no regression), mypy --strict clean, ruff clean, deprecation-free.

All 8 acceptance criteria DONE — demonstrated live via the registered console-script (AC1–AC5, AC7) and by structural test (AC6) / gate output (AC8).

What went well

  • The verify-only invariant was made a test, not a convention. The load-bearing property — the running server never reaches jwt.encode — is enforced by two complementary checks in test_mint_invariant.py: a source grep (jwt.encode appears only in mint.py) and a fresh-interpreter subprocess import proving app:app never loads mint. Adding the first production jwt.encode caller without weakening the guarantee is the whole point of the task, and it is now regression-proof.
  • Subprocess isolation defeated sys.modules pollution. test_mint.py imports mint at module load, so an in-process reachability check would be permanently poisoned. Running the app-import probe in a fresh sys.executable is the only way to observe the clean import graph — recognised at design, not discovered as a flaky test.
  • The design's "alternatives considered" killed the runtime-auth-import path early. Importing auth._ALGORITHMS[0] at runtime would have dragged FastAPI into the CLI's import graph. The chosen module-local _MINT_ALGORITHM = "HS256" pinned to the verify side by an equality test keeps the CLI to argparse+pyjwt+config and leaves shipped auth.py untouched.
  • Env-only secret closed the AP#5 surface by construction. No --secret flag exists (parser-introspection test asserts it), the key only comes from BILTIQ_JWT_SECRET, and a test asserts the failure message names the var but never echoes a value — so the signing key cannot land in argv/ps/shell history.
  • Atomic-step discipline survived a mid-task context compaction. Two clean commit boundaries (code+tests, then docs) meant the compaction between Build and Review landed on a green boundary — nothing to reconstruct.

What went wrong (caught in self-review / Review / Test)

  • AC7 console-script absent at first Test run — packaging-lifecycle gap. The first per-AC demonstration failed with No such file or directory for biltiq-privacy-mint: the package had been installed editable before the [project.scripts] entry was added, so the binary was never materialized into venv/bin. Not a code defect — the unit tests call mint.main() directly and passed throughout — but it proves the entry-point wiring is a distinct failure surface that in-process tests structurally cannot cover. Fixed by uv pip install -e to regenerate entry points, then re-demonstrated cleanly.
  • Tooling assumption: pip not in the uv-managed venv. First reinstall attempt used python -m pip → No module named pip. Switched to uv pip install. Minor, but a reminder that this repo's venv is uv-managed with no pip seeded.

What we missed (slipped past, recurred, or only caught late)

  • AC7's "console-script registers" was only exercised at Test, not Review. Review confirmed the pyproject.toml entry textually but did not attempt an install — so the stale-editable-install gap surfaced one step later than it could have. The cost was low (a reinstall), but a "fresh-install-and-invoke" check belongs in the packaging review slice, not only in Test.
  • The curator-strips-MEMORY.md hazard from BILTIQ-013 is still live. Not re-hit this task (no manual "Recent decisions" edit was attempted), but the same non-durability applies to any ADR-0007 amendment pointer. Carried forward, not resolved.

Process changes proposed (pending Friday review)

  • Add a packaging "fresh-install-and-invoke" check to the Ship/Review packaging slice. Any task that adds or changes a [project.scripts] entry should, in Review, run an editable (re)install in a scratch venv and invoke the new console-script with --help — so console-script registration is verified before Test. This would have caught the AC7 gap one step earlier.
  • Note uv-managed-venv tooling in the repo's test/build docs. The venv has no pip; gate/install commands should use uv pip. A one-line note in stack.md or the test runbook avoids the No module named pip stumble.
  • MEMORY.md "Recent decisions" durability (carried from BILTIQ-013). Still worth fixing: source "Recent decisions" from memory-stream events or wrap it in an auto: marker so hand-edited ADR pointers stop being wiped on the next curator run.
