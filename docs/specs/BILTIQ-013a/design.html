Chosen Approach

Name

Isolated console-script module: a self-contained biltiq_privacy_server/mint.py with its own main(argv), the single jwt.encode caller in production, imported by nothing in the app:app ASGI graph. The mint is a sibling of cli.py, not a subcommand of it: cli.py registers biltiq-privacy-server and lives in the server's import surface, so adding a mint subcommand there would drag jwt.encode into the runtime graph and break the verify-only invariant the parent task was built on. The mint module imports only stdlib (argparse, os, sys, datetime), jwt, and two constants from existing server modules — never app, auth's verify path, dependencies, or any router.

Description

Module layout (mint.py). The module mirrors cli.py's shape: a build_parser() -> argparse.ArgumentParser, a thin main(argv: Sequence[str] | None = None) -> int console-script entry, and small pure helpers between them. Decomposed into four testable units so each AC has a direct seam:

  • build_parser() — declares --sub (required), --ttl (type=int, default 3600), and --claim (action="append", repeatable, default None). It declares no --secret action — AC2's structural guarantee is that this parser has no secret-bearing flag, asserted by a test that walks parser._actions / parse_args option strings.
  • _parse_claims(raw: list[str] | None) -> dict[str, str] — splits each k=v on the first = (str.split("=", 1)), rejecting a token with no = and rejecting any key in the reserved set _RESERVED_CLAIMS = frozenset({"sub", "iat", "exp"}). On a bad pair it raises a small module-local MintError carrying an actionable message; values stay strings (AC5; JSON-typed values are spec § Out of Scope).
  • _build_payload(sub, ttl, claims) -> dict[str, object] — composes the claim set: now = datetime.now(UTC) (tz-aware, satisfies ruff DTZ), then {"sub": sub, "iat": now, "exp": now + timedelta(seconds=ttl)} merged with the validated extra claims. Because the reserved-claim guard already ran, extra claims can never shadow sub/iat/exp. Shape is byte-for-byte the same as tests/conftest.py::_mint_token, so the token verifies against verify_token unchanged (AC1, AC4).
  • _read_secret() -> str — reads os.environ.get(config._JWT_SECRET_ENV); empty/unset raises MintError with the AC3 message. The constant is imported, not re-spelled, so the mint and the server can never disagree on the env-var name (AC2).

argparse + error → exit-code → stderr handling. --ttl being non-positive is rejected in main (argparse cannot express "> 0" declaratively without a custom type; a _positive_int converter keeps the message uniform with the other MintError paths — chosen over a post-parse check so argparse owns the usage line). The happy path computes the payload, calls token = jwt.encode(payload, secret, algorithm=_MINT_ALGORITHM), writes the token plus a trailing newline to sys.stdout, and returns 0. Every error path (missing secret, malformed claim, reserved claim, non-positive ttl) writes one actionable line to sys.stderr, writes nothing to stdout, and returns a non-zero code (2). argparse's own usage errors (missing --sub) already exit non-zero on stderr — consistent. stdout carries the token and nothing else (AC1) — no banner, no log line, no secret echo (AC3). The signing key is never an argparse action, never printed, never logged.

Algorithm constant — own constant, drift pinned by test (dev decision 2026-06-21). The verify side pins auth._ALGORITHMS = ["HS256"]. The mint signs with the same single algorithm via a module-local constant _MINT_ALGORITHM = "HS256" — it does not import auth at runtime. Rationale: auth.py imports fastapi, so reading auth._ALGORITHMS[0] would drag fastapi into the lightweight mint CLI's import graph (the CLI should need only argparse + pyjwt + config), and it would reach into a private (_-prefixed) name. Instead, drift from the verify side is caught by an explicit equality assertion in tests/test_mint.py: assert mint._MINT_ALGORITHM == auth._ALGORITHMS[0] (the test may import auth; only the runtime CLI must stay light). This matches the repo's established "pin invariants via a test" pattern (cf. the OpenAPI drift test). The shipped high-risk auth.py is left untouched. The alternatives (import auth._ALGORITHMS[0] at runtime; hoist a shared constant into config.py and edit auth.py) are recorded in § Alternatives.

No coupling to load_settings() (spec constraint). The mint reads BILTIQ_JWT_SECRET directly via config._JWT_SECRET_ENV and does not call load_settings(), which mandates BILTIQ_HMAC_KEY the mint has no use for. Importing config for the one constant is cheap and side-effect-free (the module-level code in config.py only defines the class + constants; no env read happens at import — that is inside load_settings()). The mint touches none of the HMAC machinery.

Console-script + module-execution parity. pyproject.toml gains a second [project.scripts] entry biltiq-privacy-mint = "biltiq_privacy_server.mint:main". A console script's return value becomes the process exit code, so main returning int wires exit codes for free. No mint entry is added to __main__.py (that file is server-CLI parity only); the mint is reached solely via its own script, keeping its import surface minimal.

Verify-only invariant — how AC6 stays true and how the test proves it

The invariant is directional and precise: the request-handling runtime (biltiq_privacy_server.app:app → routers → dependencies → auth.verify_token) must never reach jwt.encode. jwt.encode lives only in mint.py and the test fixture. The mint's runtime imports are argparse + pyjwt + config only — it does not import auth at runtime (the algorithm constant is module-local, with drift caught by a test). The forbidden direction is app → mint, which this design never introduces — app.py, cli.py, the routers, and dependencies.py are untouched, so nothing in the app graph imports mint.

AC6 structural test approach (for Plan to implement)

A single structural test (tests/test_mint_invariant.py) asserts the invariant without running a server, in two complementary checks so a regression in either direction fails:

  • Reachability walk (primary). Import biltiq_privacy_server.app, then transitively collect the loaded biltiq_privacy_server.* submodules reachable from it (walk sys.modules filtered to the package prefix after importing app, or recurse module.__dict__ for module objects under the prefix). Assert mint is not among them, and assert that for every reachable module, its source does not contain a jwt.encode call. The simplest robust form: after import biltiq_privacy_server.app, assert "biltiq_privacy_server.mint" not in sys.modules (it must not have been pulled in), which directly encodes "the app graph does not import the mint."
  • Source grep (secondary, belt-and-braces). Read the source of every *.py under biltiq_privacy_server/ except mint.py and assert none contains the substring jwt.encode; then read mint.py and assert it does (so the test fails if the encode call is ever moved out of the dedicated module). This is the same shape as BILTIQ-013's "only auth.py imports jwt" intent, extended to pin where encode may appear.

The test imports biltiq_privacy_server.app (needs the two env vars seeded — the existing conftest.py os.environ.setdefault already covers collection) and the stdlib sys / importlib / pathlib — no network, no model load.

Data Model / Contract

No persistence, no wire schema, no server contract change. The only contract is the CLI surface and the minted claim shape, which must match the verify side so tokens round-trip through auth.verify_token unchanged.

Claim payload (identical to conftest._mint_token)

now = datetime.now(UTC)                     # tz-aware UTC (ruff DTZ-clean)
payload = {
    "sub": <--sub>,                          # required
    "iat": now,                              # PyJWT encodes datetime → epoch int
    "exp": now + timedelta(seconds=<--ttl>), # default ttl 3600s; must be > 0
    **<validated --claim k=v pairs, string values>,
}
token = jwt.encode(payload, secret, algorithm=_MINT_ALGORITHM)   # HS256, single call

CLI surface (design-final)

FlagType / defaultRule
--substr, requiredSets the sub claim. Missing → argparse usage error (non-zero, stderr).
--ttlint (positive), default 3600Sets exp = iat + ttl seconds. Non-positive → rejected (stderr, non-zero) via _positive_int.
--claimstr, repeatable (append)k=v merged as string value. No = → rejected. k ∈ {sub,iat,exp} → rejected.
(no --secret)—Secret is read only from BILTIQ_JWT_SECRET (AC2). Unset/empty → rejected (AC3).

stdout = the token, newline-terminated, nothing else (AC1). All diagnostics → stderr. Exit 0 on success, non-zero (2) on any error.

Security & Compliance Notes

Compliance mode: on_prem_preferred. The mint makes no cloud / external AI call — it is a local HMAC-SHA256 signing operation over PyJWT (already an approved local crypto dependency; no new dependency, so no new ADR is triggered — ADR-0007 is amended, not created). The signing-key handling rules:

  • Secret never in argv. No --secret flag exists (AC2), so the signing key cannot land in ps, shell history, or a process listing. It is read once from BILTIQ_JWT_SECRET via the shared constant.
  • Secret never logged or printed. The mint emits no log records; stdout is exclusively the token (AC1); stderr error messages name the env var but never echo its value (AC3).
  • Token is a secret-equivalent. It goes to stdout by design (the operator captures it into a variable); the README documents that minted tokens are short-lived bearer credentials and should be treated like the secret — not committed, not logged.
  • Algorithm pinned to HS256 via a module-local _MINT_ALGORITHM, with an equality test against auth._ALGORITHMS[0] guarding drift — the mint cannot sign with a weaker/other algorithm, and the verify side stays a single-element allow-list (no alg-confusion surface introduced).
  • Verify-only runtime preserved — the running server still never reaches jwt.encode (AC6, § Invariant note). The mint is an operator/CI tool, not a new auth surface on the server.

No-PII concern: the mint handles no document text — only operator-supplied claim strings (sub, optional k=v). It does not touch the detector, the HMAC pseudonymiser, or any privacy path.

Performance Considerations

Negligible and off the request path. The mint is a one-shot process: argparse parse, one datetime.now(UTC), one HMAC-SHA256 jwt.encode (microseconds), one stdout write. No model load, no network, no server import-graph cost — importing config for one constant and auth for the algorithm scalar is sub-millisecond and side-effect-free (neither does an env read at import). There is no latency budget to defend; the tool exits immediately.

ADR-0007 amendment (proposed exact wording)

Append to ADR-0007 as a dated amendment (do not rewrite the original decision):

Amendment — 2026-06-21 (BILTIQ-013a): operator token-mint carve-out. The original decision recorded that "production code contains no jwt.encode call — only the test fixture mints tokens." BILTIQ-013a adds a first-class operator helper, the biltiq-privacy-mint console-script (biltiq_privacy_server.mint), which does call jwt.encode to produce a short-lived HS256 token for smoke tests, curl against a fresh deployment, and CI. The verify-only guarantee is amended, not broken, and is now stated precisely: the request-handling runtime — the biltiq_privacy_server.app:app ASGI graph (routers → dependencies → auth.verify_token) — never reaches jwt.encode. The mint module is the single production jwt.encode caller and is imported by nothing in that graph (a structural test asserts mint is absent from the imported app module graph, and that encode appears only in mint.py). The secret is read env-only from BILTIQ_JWT_SECRET (no --secret flag — a signing key in argv would leak into ps / shell history); the algorithm is the same single-element HS256 allow-list as the verify side (mint uses a module-local _MINT_ALGORITHM with an equality test pinning it to auth._ALGORITHMS[0], catching drift at test time without runtime coupling). No new dependency is introduced (PyJWT already present); HS256-only and verify-side pinning are unchanged.

Duplication / drift risks to flag

  • Algorithm literal lives once in mint.py as _MINT_ALGORITHM = "HS256" and is pinned to the verify side by an equality test (mint._MINT_ALGORITHM == auth._ALGORITHMS[0]); if the verify side ever changes its single allow-listed alg, that test fails until the mint is updated — drift cannot ship silently.
  • Env-var name must not be re-spelled. mint.py imports config._JWT_SECRET_ENV; a literal "BILTIQ_JWT_SECRET" in mint.py is a drift bug.
  • Claim shape must stay identical to conftest._mint_token / verify_token's expectations. If the verify side ever adds a required claim (e.g. aud), the mint and its round-trip test must move together — pinned by AC1's verify-round-trip test.
  • Do not import app from mint (or vice versa). The mint may read constants from config/auth, but importing app would pull the whole runtime graph and an env read into the mint, and any future app → mint import would break AC6 — guarded by test_mint_invariant.py.
