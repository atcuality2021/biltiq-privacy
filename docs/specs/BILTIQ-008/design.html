Approach

Name

Decouple-don't-rewrite port into one stateless free-function module core/generaliser.py, with an inject-with-default region_map seam.

Description

CDSCO's backend/modules/anonymisation/generaliser.py is already framework-free (pure re + stdlib, no settings, no DB), so the port is a near-verbatim lift into packages/python-core/biltiq_privacy/core/generaliser.py — the exact module name stack.md line 65 reserves. We preserve every behaviour exactly: the _AGE_BRACKETS bands, the _REGION_MAP state→region table, each function's regex and output format, and the _GENERALISER entity-type dispatch dict (keys IN_AADHAAR, IN_PAN, IN_PHONE, PHONE_NUMBER, LOCATION, ADDRESS, HOSPITAL).

The module stays a set of module-level free functions (mirroring core/doc_hasher.py), not a key-bound class like Pseudonymiser — generalisation is stateless and holds no key. Two decoupling changes from CDSCO: (1) the module-level _REGION_MAP default is exposed through an inject-with-default seam — generalise_location and generalise_text take an optional keyword-only region_map that defaults to the bundled Indian table, so a future region pack overrides without editing core (AC4; full pack loader deferred to Phase C). (2) generalise_text's loop input is typed as list[GeneralisationSpan] — a new TypedDict {entity_type, text, pseudonym_token} defined in this module — replacing CDSCO's bare list[dict] to keep mypy --strict clean. The BILTIQ-012 orchestrator assembles each span from BILTIQ-007's Detection + AuditRecord (which between them carry all three fields); we do not edit the shipped BILTIQ-007 types. The module docstring names the CDSCO origin and states explicitly that this is rule-based generalisation, NOT a dataset-level k-anonymity guarantee (measurement is BILTIQ-021) — the AC5 no-overclaim contract.

Alternatives Considered

#AlternativeWhy Rejected
1Key-bound class like Pseudonymiser (state injected in __init__)Generalisation is stateless and holds no key/secret; a class adds ceremony with no instance state. doc_hasher's free-function shape is the right precedent.
2Edit BILTIQ-007 Detection/AuditRecord to carry entity_type+text+pseudonym_token together, then reuse one of them as the generalise_text inputNeither shipped 007 type carries all three fields, and BILTIQ-007 is closed/shipped code; mutating it risks behaviour drift in a frozen surface. A new GeneralisationSpan TypedDict in this module is additive and leaves 007 untouched (resolved open question).
3Build the full Phase-C region-pack loader now (file/entry-point discovery for region maps)YAGNI — the spec defers the loader to Phase C and only needs the inject-with-default seam today. The optional region_map keyword is the minimal forward-compatible hook.
4Reuse a generic anonymisation / k-anonymity library (e.g. an off-the-shelf generaliser)stack.md lists none, the library core is deliberately framework-free, and the rules are India-specific (Aadhaar/PAN/phone formats, state→region map). A dependency would add surface for behaviour we must preserve verbatim from CDSCO.
5Keep generalise_text's loop input as a bare list[dict] (CDSCO verbatim)dict without a value type trips mypy --strict and the no-Any rule; a narrow TypedDict documents the contract while preserving the runtime shape (same access keys).

Data Model Changes

One new in-module type: GeneralisationSpan(TypedDict) with keys entity_type: str, text: str, pseudonym_token: str. It is the input shape for generalise_text; the BILTIQ-012 orchestrator assembles it from BILTIQ-007's Detection (carries entity_type + text) and AuditRecord (carries pseudonym_token). No schema, no JSONL field, no SQLite table. No edits to the shipped BILTIQ-007 Detection / AuditRecord types — they remain frozen.

API Contract Changes

New public surface under biltiq_privacy.core.generaliser (re-exported from biltiq_privacy.core). No existing contract changes — the module is new and the 007 types are untouched. All signatures fully typed; no Any, no type: ignore.

# core/generaliser.py
class GeneralisationSpan(TypedDict):
    entity_type: str
    text: str
    pseudonym_token: str

def generalise_age(age: int) -> str: ...
def generalise_date(date_str: str) -> str: ...
def generalise_location(location: str, *, region_map: dict[str, str] | None = None) -> str: ...
def generalise_phone(phone: str) -> str: ...
def generalise_aadhaar(aadhaar: str) -> str: ...
def generalise_pan(pan: str) -> str: ...
def generalise_text(
    pseudonymised_text: str,
    spans: list[GeneralisationSpan],
    *,
    region_map: dict[str, str] | None = None,
) -> str: ...

No new environment variables. No CLI change. No network, no config read.

Security & Compliance

  • Compliance mode on_prem_preferred: no external / cloud AI call, no network, no LLM, no config/DB/FastAPI import (AC3). Pure re + string ops. No external AI dependency introduced → no ADR required. The framework-free auto-block in code review is satisfied.
  • No key, no secret, no env read inside python-core — the module is stateless and holds nothing sensitive.
  • No PII logged: the module has no logging call and no print(). It receives already-pseudonymised text and detected span values and returns coarsened strings; it never emits inputs.
  • Output is coarser-than-input by construction (brackets, month/year, region rollup, suffix/middle masking), supporting the AC6 irreversibility property.
  • Input escaping: outputs are fixed-format strings (no user input echoed into a markup/shell context); the span text is read only to compute a generalised value, never reflected verbatim.

Performance Considerations

Negligible. Each generaliser is a single regex match or dict lookup over a short string. generalise_text is O(n) in the number of spans, each doing one dispatch-dict lookup and one bounded str.replace(..., 1) — linear in spans, no quadratic re-scan. Comfortably inside the overview.md budget ("Pseudonymisation + generalisation + audit row: <1 ms"); not a hot path relative to Presidio detection. No caching needed.

Risks

RiskSeverityMitigation
Date-parse ordering ambiguity: CDSCO's generalise_date regex (\d{1,2})[/\-](\d{1,2})[/\-](\d{4}) takes group(2) as the month, i.e. it assumes DD/MM/YYYY. A MM/DD/YYYY input mis-maps the month (and 13/05/2020-style values where group(2) > 12 fall through to [DATE_REDACTED]). The spec does not resolve input date ordering. MED Port verbatim — preserve the DD/MM assumption (India-centric default, consistent with the India region map). A characterization test pins the DD/MM behaviour and the [DATE_REDACTED] fallback explicitly so the assumption is documented, not silent. Cross-locale date handling is out of scope (region packs, Phase C). Flag for the dev: confirm DD/MM is the intended default before Build.
Behaviour drift from CDSCO during the port (bracket boundaries, region strings like "Healthcare Facility, <region>", phone/aadhaar/pan mask formats, dispatch keys). MED Characterization tests (AC6) pin each function's golden output and the seven _GENERALISER dispatch keys against synthetic inputs; copy the regex and format strings byte-for-byte from the CDSCO source.
Irreversibility is an AC6 property but a per-span replacement, not a dataset-level guarantee — risk of overclaiming k-anonymity. LOW AC5 no-overclaim docstring states this is rule-based generalisation, not a k-anonymity guarantee (measurement is BILTIQ-021). Tests assert the per-value irreversibility property only (output ≠ input, exact value not recoverable from output alone).
Phantom "ABHA" generaliser from an earlier problem statement could creep back in. LOW Resolved open question: there is no CDSCO ABHA generaliser — port exactly the six functions and the seven dispatch keys, no more.

Coordination: core/generaliser.py is a fresh file; no in-flight task touches it. BILTIQ-006 (per MEMORY.md) is in scripts/ memory-spine, disjoint. The GeneralisationSpan type and generalise_text are the contract BILTIQ-012 will consume; this design freezes that surface.
