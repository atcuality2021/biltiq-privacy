Problem

The repo vendors a memory-spine toolchain (scripts/_memory_curator.py + scripts/_memory_writer.py, BILTIQ-003) at the schema shape of plugin biltiq-engineering v1.6.x — 3 auto-sections (current_focus / code_areas / session_log), 4 event types (standup_post, blocker_logged, commit_metadata, reflect_note), <!-- auto:<name>:start/end --> marker-based splice. The plugin has since shipped v1.10.1, which owns 6 auto-sections (active_task, today_activity, open_blockers, recent_decisions, open_questions, doctor_installs) via heading-prefix splice (no marker comments), reads a different event vocabulary (task_state_change, commit, scan_result, blocker_open/blocker_close, decision, doctor_install), and enforces per-event JSON schemas from a scripts/memory_schemas/ directory. The plugin's curator fires from SessionStart + PostToolUse hooks regardless of what the repo vendors. When it runs against MEMORY.md, it sees the dev's hand-written headings (## Active task, ## Today's activity, ## Recent decisions, ## Open questions, ## Open blockers) sitting inside the <!-- manual:start/end --> envelope, claims them as its sections by prefix match, splice-replaces the dev-written content with empty-state placeholders (_(no decisions recorded)_, _(no task state recorded yet)_, etc.), and inserts a fresh ## Doctor installs section it owns but the repo has never had. Reproduction: open this session, do nothing, run git diff MEMORY.md — 42 lines of drift wiping real content. Meanwhile /biltiq-engineering:standup emits standup_post events with {yesterday_summary, today_task, branch, blockers} that the repo curator reads as {date, doing}, rendering an empty **Today (?):**; the dev has been hand-emitting a second compatibility event with the old shape as a workaround (see .biltiq/memory-stream.jsonl 2026-05-28 14:14:06 immediately after the procedure-shape event at 14:12:59). Both symptoms have the same root cause: the vendored toolchain is stale relative to plugin v1.10.1.

User Impact

Operational. After this ships:

  • MEMORY.md stops drifting on session-start. The diff between two consecutive SessionStart events with no user activity is zero lines (verified by AC8 reproduction script).
  • /biltiq-engineering:standup + /biltiq-engineering:reflect + /biltiq-engineering:build emit single events that render correctly the first time, with no need for the dev to hand-emit a second compatibility event.
  • The repo can be used outside Claude Code (CI, fresh checkout on a non-plugin machine, headless agents) and still get correct curation — the vendored copy stays as the source of truth on-disk, with the plugin acting as a transparent cache. This is the fork-and-stay direction recorded in ADR-0004.
  • Historic .biltiq/memory-stream.jsonl events from BILTIQ-001/002/003/004 keep rendering — old event types are tolerated as "unknown, project-but-skip" rather than rejected. AC11 covers the back-compat tolerance.
  • Operators get a reproducible install path: bash scripts/install-curator-hook.sh wires up both the SessionStart + PostToolUse + post-commit hooks in one pass, idempotently.

Acceptance Criteria

  • OPEN AC1 — Four spine files in scripts/ are byte-equivalent to their plugin v1.10.1 sources at ~/.claude/plugins/cache/biltiq-internal/biltiq-engineering/1.10.1/scripts/, modulo a header comment block that records the source plugin version + sync date + ADR-0004 reference: _memory_curator.py, _memory_writer.py, _memory_reader.py, and the transitively-required sibling _paths.py (imported by all three spine modules as from _paths import _resolve_repo_root, _repo_hash, _safe_write). Validation: diff <(sed '/^# SYNC-HEADER:/,/^# END-SYNC-HEADER/d' <repo_file>) <(plugin_path) exits 0 for each file. The sync-header block is the only divergence permitted; any other delta requires an ADR update.
  • OPEN AC2 — scripts/memory_schemas/ directory exists and contains all 14 JSON Schema files the v1.10.1 writer ships with — vendoring the full set (not just the 7 the curator currently renders) preserves AC1's byte-equivalence spirit and avoids silently dropping events the standup / EOD / compliance skills emit. Files: blocker_close.json, blocker_open.json, commit.json, compliance_flag.json, decision.json, doctor_install.json, eod_post.json, estimate_actual.json, routing_payload.json, scan_result.json, security_flag.json, standup_post.json, task_state_change.json, vllm_quality_warning.json. Each file byte-equivalent to the plugin's scripts/memory_schemas/ contents at v1.10.1. scripts/_memory_writer.py loads them via the existing SCHEMAS_DIR resolution. Additionally, root pyproject.toml declares jsonschema as a dev-dependency under [tool.uv].dev-dependencies (the writer imports from jsonschema import Draft7Validator; graceful-degrade is not an acceptable resting state).
  • OPEN AC3 — MEMORY.md restructured to remove the three obsolete <!-- auto:<name>:start/end --> marker pairs (current_focus, code_areas, session_log) — the v1.10.1 curator uses prefix splice and ignores these. The <!-- manual:start --> ... <!-- manual:end --> envelope is retained for dev-owned narrative content (## Project at a glance, ## Recently completed, ## Known issues & gotchas, ## Conventions specific to this repo, ## Glossary deltas, ## Archive). The six plugin-owned headings (## Active task, ## Today's activity, ## Open blockers, ## Recent decisions, ## Open questions, ## Doctor installs) move outside the manual envelope so the plugin's prefix splice owns them cleanly. Hand-written content currently inside those headings (e.g. the 4 process-change bullets in ## Recent decisions, the BILTIQ-004 entry in ## Active task) is preserved by backfilling matching events to .biltiq/memory-stream.jsonl per AC4.
  • OPEN AC4 — A one-shot backfill script scripts/_backfill_memory_v1_10.py ports the dev-curated content from MEMORY.md's pre-migration state into the v1.10.1 event vocabulary: each ## Recent decisions bullet becomes a decision event with appropriate category / status / summary; each ## Open questions bullet becomes a decision event with status=deferred; the active ## Active task entry becomes a task_state_change event. Backfill events carry ts matching their original date if known (BILTIQ-003 dates from git log), or the migration date otherwise, with a payload field backfilled: true for auditability. Script is idempotent (re-run is a no-op) and writes events through scripts/_memory_writer.write_event so JSON-schema validation gates them. Script is deleted after one successful run — AP#7 (debug residue) defence — and the deletion lands in the same PR as part of the cleanup step.
  • OPEN AC5 — Existing repo tests at tests/scripts/test_memory_curator_io.py, test_memory_curator_projection.py, test_memory_writer.py, test_hook_install.py are replaced by ports of plugin v1.10.1's tests/spine/test_curator.py + test_writer.py + any matching reader/hook tests. The ported suite covers: (a) one projection test per renderer (active_task / today_activity / open_blockers / recent_decisions / open_questions / doctor_installs), (b) schema-rejection test per event type (writer drops unknown event types + schema-invalid payloads with return False, no exception), (c) cap-and-archive test for the three ARCHIVABLE sections, (d) marker-absence test asserting the v1.6 <!-- auto:*:start --> markers are no longer recognised, (e) concurrent-lock test via fcntl.flock. Total test count ≥ 18, target 100% green.
  • OPEN AC6 — scripts/install-curator-hook.sh installs three hooks idempotently in one pass: (a) .git/hooks/post-commit wiring the curator (existing behaviour from BILTIQ-003), (b) a Claude-Code SessionStart hook registration at .claude/hooks/session-start/curator.sh mirroring the plugin's, (c) a PostToolUse hook registration. Re-run with no changes is a no-op; re-run after an upstream plugin version bump prints a one-line "plugin version drift detected, re-run with --force to re-sync" warning. Flags: --force, --uninstall, -h/--help. Style mirrors scripts/install-age.sh from BILTIQ-004.
  • OPEN AC7 — docs/adr/0004-memory-spine-vendoring.md is added at status proposed during the Build phase, dated 2026-05-29; status flips to accepted at Step 6 Ship of this same task (matches the ADR-0001 / ADR-0002 / ADR-0003 precedent — ADRs ride alongside the implementation through Build → Review → Test, and the status flip is the Ship-time witness that the decision has survived adversarial review and CI-green merge). Out of Scope

  • Pushing the v1.10.1 schema upstream into a public PyPI package — the ADR-0004 exit criterion. Until the plugin ships a pip-installable surface, we vendor. That packaging work is a separate ticket.
  • Reformatting the existing memory-stream.jsonl from v1.6 event types into v1.10.1 event types — the legacy events stay as-is (append-only contract; we never rewrite history). The back-compat tolerance from AC11 means they're skipped on projection; only new events from BILTIQ-006 onwards get the v1.10.1 shape.
  • Auto-detecting plugin version bumps and re-syncing on the fly — manual --force re-sync via scripts/install-curator-hook.sh is the contract. Auto-resync risks introducing untested upstream changes mid-session.
  • Schema migration for upcoming plugin versions beyond v1.10.1 — out of scope. When v1.11 ships, a new ticket lands with the diff.
  • Replacing the entire memory-spine with a different persistence model (sqlite, Redis, etc.) — wholly out of scope. The append-only JSONL contract from BILTIQ-003 stays.
  • Restructuring how the /biltiq-engineering: skills emit events — the skills already emit the v1.10.1 event vocabulary correctly (we saw standup_post with {yesterday_summary, today_task, branch, blockers} at .biltiq/memory-stream.jsonl 2026-05-28 14:12:59). The only mismatch was on the consumer side. Skill-side changes are out of scope.
