Approach

Name

Description

This PR is a schema-version port, not a behavioural rewrite. The 370-LOC BILTIQ-003 curator + 92-LOC writer (v1.6 shape: 3 auto-sections delimited by <!-- auto:<name>:start/end --> markers, 5-event vocabulary, stdlib-only) is wholesale replaced by the 636-LOC v1.10.1 curator + 425-LOC v1.10.1 writer + 138-LOC v1.10.1 reader (6 auto-sections via heading-prefix splice, ~10-event vocabulary with optional JSON-schema validation, sibling _paths.py helper, archive overflow into .biltiq/memory-archive/YYYY-MM.md). All behaviour comes from the byte-equivalent v1.10.1 source — this design specifies what gets vendored, where the seams sit, and how drift is detected, not how the curator works internally. The runtime semantics are owned by the upstream plugin's design documents (referenced from ADR-0004).

Five files leave the plugin's scripts/ directory and land under scripts/ in this repo with one extra comment block prepended: _memory_curator.py, _memory_writer.py, _memory_reader.py, _paths.py (sibling import dependency surfaced during input review — OQ-D3 resolved by amended AC1 wording), plus memory_schemas/ (all 14 event-type JSON schemas the plugin ships per OQ-D1 resolution: blocker_close.json, blocker_open.json, commit.json, compliance_flag.json, decision.json, doctor_install.json, eod_post.json, estimate_actual.json, routing_payload.json, scan_result.json, security_flag.json, standup_post.json, task_state_change.json, vllm_quality_warning.json). The header block records source plugin version + SHA256 hashes captured at PR-open + sync date + an ADR-0004 cross-link. AC1's diff <(sed '/^# SYNC-HEADER:/,/^# END-SYNC-HEADER/d' ...) validation isolates the header as the only permitted delta. The vendored writer's jsonschema dependency is declared in root pyproject.toml under [tool.uv].dev-dependencies per OQ-D2 resolution — fail-fast at uv sync time rather than silent no-op at first event-write.

MEMORY.md restructures: the three v1.6 marker pairs (<!-- auto:current_focus:start/end -->, <!-- auto:code_areas:start/end -->, <!-- auto:session_log:start/end -->) are deleted (the v1.10.1 curator ignores them — prefix splice). The six plugin-owned headings (## Active task, ## Today's activity, ## Open blockers, ## Recent decisions, ## Open questions, ## Doctor installs) move outside the <!-- manual:start/end --> envelope so the curator's prefix-match owns them cleanly; today's collision (the curator finds those headings inside the manual envelope and rewrites them with empty-state placeholders) disappears once the envelope no longer contains them. Dev-curated content inside those six headings is preserved via a one-shot backfill (scripts/_backfill_memory_v1_10.py, AC4) that emits matching events through the new v1.10.1 writer; the backfill script is deleted in the same PR after one successful run (Anti-Pattern #7 hygiene). The <!-- manual:start/end --> envelope is retained around the six dev-owned narrative sections (## Project at a glance, ## Recently completed, ## Known issues & gotchas, ## Conventions specific to this repo, ## Glossary deltas, ## Archive) because the v1.10.1 curator preserves non-matching sections verbatim — the envelope is now belt-and-braces, not load-bearing, but keeping it documents the dev-owned boundary for human readers.

The four existing test files in tests/scripts/ (test_memory_writer.py, test_memory_curator_io.py, test_memory_curator_projection.py, test_hook_install.py — 20.8 KB combined) are replaced by ports of plugin v1.10.1's tests/spine/test_curator.py + test_writer.py + test_reader.py. test_hook_install.py stays in shape but is rewritten against the new installer (AC6 — three hooks: post-commit, SessionStart, PostToolUse).

The trade-off accepted: this is the fork-and-stay direction (ADR-0004), not de-vendoring. The repo keeps a synced copy so CI, fresh checkouts on non-plugin machines, and non-Claude-Code clients can curate; the plugin is treated as a transparent cache. The cost is one sync gate (scripts/_check_spine_sync.py) that diffs vendored vs plugin paths and soft-warns on drift for 30 days post-merge, hard-gating thereafter via BILTIQ-006-followup-1 (a separate ticket, Q3 resolution). The benefit is a working repo regardless of the operator's Claude Code plugin state and a single source of truth for what the curator does at any given commit.

(c) Cross-cuts other repos — a developer working on biltiq-privacy and biltiq-engineering simultaneously would have to swap plugin versions per repo. 4Fork the plugin curator with local-only modifications. Local-only modifications fork the upstream contract and make every future v1.11 sync a manual merge. The right shape is byte-equivalent vendoring + a one-shot data migration (AC4 backfill) + a structural restructure of MEMORY.md (AC3) to match what the curator expects.

Auto-section count

3 → 6. v1.6 owned current_focus / code_areas / session_log (marker-splice). v1.10.1 owns active_task / today_activity / open_blockers / recent_decisions / open_questions / doctor_installs (heading-prefix splice, no marker comments). Caps + archive policy (from plugin curator constant CAPS): active_task: 1 entry, no archive; today_activity: 15 lines, no archive; open_blockers: 10 lines, archive overflow; recent_decisions: 5 lines, archive overflow; open_questions: 10 lines, FIFO + archive; doctor_installs: 5 lines, no archive. Archive file path: .biltiq/memory-archive/YYYY-MM.md (per-machine, gitignored — new artifact).

Stream-line shape change

v1.6 wrote {schema_version: 1, ts, event_type, payload: {...}} (payload nested). v1.10.1 writes {schema: "v1", event_type, ts, <payload-keys-flat>} (flat record). Reader's schema_version-vs-schema check: v1.10.1 reader silently skips lines where schema != "v1"; v1.6 lines lack schema entirely and are also skipped — AC11 says this is fine, the events are tolerated (no crash), not rendered.

All API surface changes are vendored from plugin v1.10.1 byte-equivalent — the design records the deltas relative to the v1.6 surface that exists in this repo today.

Security & Compliance

  • Compliance mode: on_prem_preferred (AGENT_RULES.md § Compliance line 23). The vendored writer reads this declaration at runtime via _read_compliance_mode() (plugin writer line 119) and routes accordingly. In on_prem_preferred mode the _strip_external_api_fields branch (plugin writer line 163) is dormant — no payload mutation. The on-prem-compliance scanner does not fire on this PR.
  • JSON schemas are in-repo data, no external fetch. All 14 schemas under scripts/memory_schemas/ (per OQ-D1 resolution) are vendored static JSON files. The writer loads them via SCHEMAS_DIR = SCRIPT_DIR / "memory_schemas" (plugin writer line 41). No HTTP fetch, no $ref resolution against external URIs, no schema-registry dependency.
  • On-prem strip semantics are vendored AND now exercisable on disk, but still inert at runtime here. The writer's _strip_external_api_fields drops any property whose schema entry sets external_api_response: true. vllm_quality_warning.json and routing_payload.json — both vendored per OQ-D1 — carry that annotation; they are the schemas that exercise the strip path. The runtime gate is _read_compliance_mode(): in on_prem_preferred mode the _strip_external_api_fields branch is never taken, so the path is exercised by tests but dormant in production. Recorded in ADR-0004 § Consequences.
  • Prompt-truncation cap. DEFAULT_TRUNCATE_LEN = 200 bytes (plugin writer line 50). Applied to PROMPT_FIELDS = {msg, message, summary, yesterday_summary, today_task, tomorrow, tech_debt, resolution}. Override via env BILTIQ_AUTO_TRACK_FULL_PROMPTS=on. This cap is sufficient for an SBOM scan — no field can carry > 200 bytes of free text by default, so a leaked password or PII string is bounded.
  • No PII on the committed projection. MEMORY.md stays committed; .biltiq/memory-stream.jsonl stays per-machine (gitignored per BILTIQ-003 design). The dev decides what crosses the trust boundary on every commit. The 200-byte truncation gives a safety net even when raw prompts contain PII.
  • No secrets in vendored code. The 1289 LOC of vendored Python (curator + writer + reader + paths) contains zero hardcoded secrets — verified by anti-pattern-scanner #5 invocation at Step 4 Review.
  • No shell=True. The curator + writer + reader do not invoke subprocesses. The installer (install-curator-hook.sh) uses argv lists for its git rev-parse call. No shell-injection class of bugs introduced.
  • SBOM impact. Dev-dependency on jsonschema >= 4.0 (PyPI, MIT-licensed) introduced by the v1.10.1 writer's from jsonschema import Draft7Validator import. Per OQ-D2 resolution, declared in root pyproject.toml under [tool.uv].dev-dependencies — uv sync installs it automatically; missing-dep cases fail fast at install time rather than producing a silent no-op spine at first event-write. The graceful-degrade try/except ImportError path in the vendored writer (plugin writer lines 34-37) is retained as a defensive net (preserves AC1 byte-equivalence) but is no longer the load-bearing fallback in this repo. Compliance call: on_prem_preferred mode says new AI dependencies require an ADR; jsonschema is a stdlib-style JSON validator, not an AI dependency. AGENT_RULES.md § Architectural decisions also says "Any new dependency requires an ADR before merge" — ADR-0004 covers this. R2 severity now LOW (was MEDIUM).

Performance Considerations

  • Curator LOC growth: 370 → 636. Adds JSON-schema validation per event, archive overflow logic, six renderers (vs three in v1.6), and the ~/.biltiq-engineering/<hash>/state/ marker-clearing dance. Measured budget unknown for this repo's stream shape; flagged as Risk R6 (new — surfaces during design, not anticipated by spec). Plugin's own design.md § 3 implies p95 < 50 ms on a 7-day / 10k-event window for the reader; curator budget is implied < 200 ms based on similar shape but not measured.
  • PostToolUse hook latency budget. The plugin's hooks/post-tool-use/hook.sh lines 75–90 fire-and-forget (( ... ) & disown); the visible commit delay is bounded by the time to fork+disown — sub-millisecond. The curator runs in the background; if it takes > 1 s, the next hook invocation may overlap, and the v1.10.1 curator's fcntl.flock on .biltiq/.curator.lock serialises. No user-visible blocking.
  • SessionStart hook latency budget. Same pattern. Background fire; fcntl.flock guards against concurrent runs.
  • Writer hot-path latency. v1.10.1 writer adds: _load_schema (cached after first load) + Draft7Validator.iter_errors + _read_compliance_mode (mtime-cached) + _truncate_prompts + _maybe_trigger_curator (two state-file reads + one stat + an empty-file touch). Plugin design comment (writer line 220) claims "well under the 50ms trigger-detection cap". For BILTIQ-006 we trust that — the writer is byte-equivalent; we cannot diverge.
  • Stream growth. v1.10.1 archives overflow into .biltiq/memory-archive/YYYY-MM.md, addressing the BILTIQ-003 tech-debt #3 ("no stream archival/rotation policy"). The stream-stream itself remains append-only and grows monotonically; archival prevents MEMORY.md growth, not .biltiq/memory-stream.jsonl growth.

R2 JSON-schema validation adds a jsonschema dev dependency. The v1.10.1 writer imports Draft7Validator from the jsonschema PyPI package. The writer has a graceful-degrade path (try: from jsonschema import Draft7Validator; except ImportError: Draft7Validator = None; write_event then returns False with a stderr warning), but in degraded mode no events are written — the spine becomes a silent no-op. AGENT_RULES.md § Architectural decisions says "Any new dependency requires an ADR before merge". LOW Mitigated by OQ-D2 resolution. jsonschema >= 4.0 is declared in root pyproject.toml under [tool.uv].dev-dependencies as part of Migration step 1, so uv sync picks it up automatically; the silent-no-op path is no longer reachable in normal install flows. The graceful-degrade try/except ImportError shim is retained inside the vendored writer because AC1 demands byte-equivalence, but it is no longer load-bearing here. ADR-0004 § Decision records the declaration; ADR-0004 § Consequences notes the retained shim as accepted vendored behaviour. on_prem_preferred compliance status: jsonschema is a stdlib-style validator, not an AI dependency; ADR-0004 is the only gate. The library wheel does not import scripts/, so the dep is scoped narrowly to repo tooling (no SBOM impact on the published wheel).
R3 Hook installer touches .claude/hooks/. The new installer (AC6) writes to the user's per-machine Claude Code config directory. Idempotency is critical — a careless overwrite could break the dev's Claude Code setup for other repos that share the cache. MEDIUM Mitigation: installer uses symlink + sentinel-file pattern from BILTIQ-004 scripts/install-age.sh's --uninstall approach. Sentinel at .claude/hooks/session-start/.biltiq-privacy-installed records what we placed. --uninstall refuses to remove anything without a matching sentinel. AC5(e) hook-install tests cover idempotency directly (run twice, single sentinel, single symlink). Risk transitions to LOW once tests land.
R4 Backfill script edits .biltiq/memory-stream.jsonl. The stream is append-only by BILTIQ-003 design contract (design.html line 158: "Append-only newline-delimited JSON"). The backfill must append, never rewrite — otherwise existing v1.6 events get clobbered and back-compat (AC11) is broken. LOW Mitigation: backfill uses _memory_writer.write_event for every emit (AC4 contract); the writer's POSIX-atomic append (and v1.10.1's fcntl.flock) guarantee append-only. Idempotency: backfill writes a sentinel event (decision with category=migration + summary=backfill_complete) as its last action; re-runs check for the sentinel and exit early. Test: test_backfill_idempotent in a new tests/scripts/test_backfill.py — short, single-purpose, deletable when the backfill script is deleted at Migration step 9.
R5 MEMORY.md restructure invalidates external references to line numbers. GH issue #7 references MEMORY.md line 85 (the standup_post payload mismatch bullet). After restructure that line moves or vanishes. Past PRs and reflect.html cross-links may break. LOW Mitigation: PR description carries a "renumber map" — a small table of {old-line, old-content-fragment, new-location}. AC10 already moves the BILTIQ-006 entry from Known issues to Recently completed via a backfilled decision event, so issue #7's content gets a new home; the renumber map closes the loop. For external readers landing on issue #7, the PR description is discoverable via the issue's "linked-by" cross-references. Acceptable cost for a one-time restructure.
R6 Curator latency at 636 LOC + per-event jsonschema validation is unmeasured for this repo's stream shape. Spec did not anticipate this risk. Plugin's own design implies it stays under budget but the actual numbers were not measured for biltiq-privacy's stream (currently ~12 events). At-scale (~10k events) the per-event validation cost could push the curator past the 200 ms hook-detection budget that BILTIQ-003 set. LOW Detection: add a one-time benchmark to the PR — time python3 scripts/_memory_curator.py on a stream pre-loaded with 10k synthetic events. Mitigation: if the wall-clock exceeds 1 s, raise it as a tech-debt entry in reflect.html and open a follow-up ticket; do not block the merge — the curator runs background-disowned via the hook, so user-visible latency is the fork+disown cost (sub-ms), not the curator runtime. Acceptable to ship without the benchmark if the dev is time-constrained; record as known-unvalidated in reflect.html.
R7 Curator-pending state file at ~/.biltiq-engineering/<hash>/state/ is per-machine, not per-repo-checkout. If the dev clones biltiq-privacy at two paths on the same machine (e.g. /home/atc/Desktop/biltiq-privacy and ~/work/biltiq-privacy), the _repo_hash function (sha1[:12] of path bytes — see plugin _paths.py) gives them distinct state dirs.
