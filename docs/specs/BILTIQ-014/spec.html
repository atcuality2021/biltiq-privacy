Problem

BILTIQ-007's HMAC pseudonymisation is one-way by design: tokens are deterministic but nothing can restore the original value. Two pressures make reversibility necessary: (1) competitive — Skyflow's tokenize/detokenize is the feature prospects benchmark, and their GenAI re-identification story depends on it; (2) internal honesty — DPDP-3 in regimes/dpdp.py attests "HMAC-based pseudonymisation allows authorised re-identification" while the library offers no re-identification path. Skyflow solves this with their vault storing the mapping; we must solve it vault-less: the mapping is encrypted with a consumer-held key and persisted by the consumer — we never hold data or keys.

User Impact

Authorised users can restore originals from pseudonymised text (support workflows, the BILTIQ-015 LLM restore leg, regulator requests) without any third party in the read path. Every re-identification is an auditable disclosure event suitable for the BILTIQ-010 hash chain. Consumers who never supply a token map keep today's strictly one-way behaviour.

Acceptance Criteria

  • OPENAC1 — core/token_map.py provides a TokenMap whose entries seal originals with a consumer-held key (AEAD; algorithm + library decided in design with an ADR). Serialisable to a versioned, documented format the consumer persists; the library performs no storage I/O.
  • OPENAC2 — Pseudonymiser gains an opt-in token_map= seam: with it, pseudonymise_text records sealed originals keyed by token; without it, output is byte-identical to BILTIQ-007 behaviour (regression-pinned).
  • OPENAC3 — reidentify(text, *, token_map, key, scope=None) restores originals byte-identically (round-trip property test); scope restricts restorable entity types — out-of-scope tokens stay tokenised.
  • OPENAC4 — Without the key (or with a wrong key), re-identification fails cleanly (typed exception, no partial plaintext); the HMAC token itself remains one-way (no oracle).
  • OPENAC5 — Every successful re-identification yields a disclosure record (who/what entity types/when via caller-supplied timestamp) shaped for audit_chain.append_row; chain integration test included.
  • OPENAC6 — Map format pinned by a golden vector (cross-language contract for the Node/PHP/Go SDKs, ADR-0005 discipline); DPDP-3's docstring/details updated to reference the real capability.

Out of Scope

  • HTTP exposure of reidentify (BILTIQ-020 policy gate decides; deny-by-default standing decision).
  • Key management service / rotation tooling — runbook documents consumer-side KMS/age patterns; rotation helper is a follow-up if demanded.
  • Format-preserving encryption of tokens (tokens keep the [TYPE_hex] shape).

Open Questions

  • AEAD via the cryptography package (new dependency → ADR required) vs sealing through the existing age wrapper (no new dep, subprocess cost per entry)? Design must weigh both; leaning cryptography + ADR.
  • Should scope live on the map (sealed-in at creation) or only at the reidentify call? Security implication either way — design decision with plan-reviewer scrutiny.
  • Same HMAC key for tokens and a derived key for sealing (HKDF), or two independent keys? Leaning HKDF derivation from one consumer secret.
