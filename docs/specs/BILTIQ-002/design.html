Approach

Name

Two-module Indian PII pack under biltiq_privacy/indian/: patterns.py as the regex single-source-of-truth + zero-dep redact() hot path, recognisers.py as a thin Presidio adapter consuming the same strings.

Description

The spec locks four invariants — eight Indian entity types, a two-module split (patterns.py pure-regex + recognisers.py Presidio adapter), no string duplication between the two (AC3), and lazy import of presidio_analyzer / spacy when only patterns is in use (AC5). Those four together force a specific topology: patterns.py imports nothing from the Presidio stack at module level; recognisers.py imports presidio_analyzer at module level and references the regex strings by name from patterns. build_engine() is a pure factory — no module-global _engine, no caching — so consumers own the singleton lifecycle (the same posture detectors/presidio_backend.py will take in v0.4.0+).

The eight regex constants land as Final[str]; the eight PatternRecognizer instances land as a module-level tuple typed Final[Sequence[PatternRecognizer]]. The PATTERNS: dict[str, re.Pattern[str]] mapping is compiled at module load in patterns.py (eight one-time re.compile calls; deterministic, no side effects). redact(text) walks PATTERNS in a fixed order, ABHA-before-AADHAAR (AC4), and substitutes each match with [REDACTED-<TYPE>]. The ordering is encoded by an explicit _REDACT_ORDER: Final[tuple[str, ...]] sequence — not by dict-insertion order — so the contract is impossible to break by a reflexive alphabetical-sort refactor.

The eight Presidio recognisers consume the compiled re.Pattern via PATTERNS[name].pattern (the raw string the recogniser stores on Pattern.regex), keeping the AC3 invariant test (_GSTIN.patterns[0].regex == GSTIN_PATTERN) trivially true. Each PatternRecognizer ships with a fixed confidence score (Aadhaar 0.95, PAN 0.9, ABHA 0.85, GSTIN 0.9, Voter 0.7, IFSC 0.85, Phone 0.9, Med Reg 0.6 to match CDSCO prod per spec § Out of Scope §7; corrected during BILTIQ-002 build — the prior draft of this section transcribed three values incorrectly: AADHAAR was 0.85, IFSC was 0.9, PHONE was 0.7; CDSCO-RegAI:backend/modules/anonymisation/presidio_engine.py is the source of truth) and a small Indian-context word list for Presidio's context-boost. build_engine(nlp_engine=None) instantiates a fresh AnalyzerEngine, registers all eight, and returns it — pure factory, no caching, no env reads, no I/O. Per spec open-question §2 the design locks the eager interpretation: callers pass a pre-built NlpEngine or None for Presidio's default — they do not pass a factory callable. Per spec open-question §3 the design locks the sub-module-only import path: biltiq_privacy/__init__.py stays as it is (no redact re-export). Both interpretations are flagged in § Open Questions Confirmed for explicit dev approval before plan.html lands.

The trade-off accepted: the dual surface (patterns.redact for hot path, recognisers.build_engine for NLP path) is mildly redundant — patterns and recognisers detect the same eight types. The redundancy is the point. CDSCO-RegAI's backend/utils/log.py needs sub-millisecond redaction inside the logging filter (no spaCy model load, no AnalyzerEngine construction); ATC CommandCenter's anonymisation pipeline needs Presidio's confidence-scored, context-aware detection. Collapsing the two into a single Presidio-only surface fails the hot path; collapsing into a single regex-only surface fails the NLP-context path. AC5 (lazy import) plus AC3 (no string duplication) together codify this trade-off as a checkable invariant rather than a comment.

Ordering enforcement for ABHA-vs-AADHAAR (chosen: explicit ordered tuple)

#AlternativeWhy Rejected / Chosen
1Rely on Python 3.7+ dict-insertion-order semantics — declare ABHA before AADHAAR in the PATTERNS literal and iterate the dict directly in redact().Order is implicit and disappears under a sort-keys refactor or an alphabetical rename (e.g. a future ruff rule that sorts dict literals). Invisible coupling between source-line position and runtime behaviour is a maintenance trap, particularly on the AC4 invariant test ("input 12-3456-7890-1234 redacts to [REDACTED-ABHA]").
2Build a single combined regex with named groups ((?P<ABHA>...)|(?P<AADHAAR>...)|...) and rely on alternation left-to-right matching.Tighter and faster, but: (a) one giant regex is hostile to AC3's per-name string export, (b) ABHA-before-AADHAAR is one of several ordering constraints we may need over time (IFSC vs PAN both have 4-letter prefixes; phone vs Aadhaar both have 10-digit overlap), and a flat alternation hides which alternative wins for which input, (c) Presidio recognisers want one regex per entity type — combining them here makes recognisers.py's consumption awkward.
3 ✓Explicit _REDACT_ORDER: Final[tuple[str, ...]] = ("ABHA", "AADHAAR", "PAN", "GSTIN", "VOTER_ID", "IFSC", "PHONE_IN", "MEDICAL_REG") consumed by redact() (chosen).Order is data, not source-line position. AC4's invariant test asserts on the tuple value itself ("ABHA index < AADHAAR index"). Future ordering tweaks land as a single-line change. Iteration cost on the hot path is 8 fixed regex sweeps per input string — same as the dict-iteration alternative.

#AlternativeWhy Rejected / Chosen
1Function-level import presidio_analyzer inside redact() ("lazy import at call time").Misreads AC5. Data Model Changes

None. No schemas, no JSONL fields, no SQLite tables, no audit-chain row changes. The PATTERNS dict and INDIAN_RECOGNISERS tuple are in-process Python data structures, not persisted state.

API Contract Changes

Two new public Python symbols ship in v0.1.0 (additive — no breaking changes; v0.1.0 itself is the first published version):

PAN_PATTERN:          Final[str]

GSTIN_PATTERN:        Final[str]

# biltiq_privacy.indian.recognisers
INDIAN_RECOGNISERS: Final[Sequence[PatternRecognizer]]   # length 8

    """Construct a fresh AnalyzerEngine and register all eight Indian recognisers.
    Pure factory — no module-global cache, no env reads, no I/O.
    Consumer owns singleton lifecycle. If `nlp_engine` is None, Presidio's default
    spaCy-based engine is used."""

Import path contract: only the leaf-module paths are blessed. from biltiq_privacy.indian.patterns import redact and from biltiq_privacy.indian.recognisers import INDIAN_RECOGNISERS, build_engine. biltiq_privacy/__init__.py stays empty of these symbols (spec open-question §3 lock) so that import biltiq_privacy remains a sub-millisecond no-op.

Structure preservation in redact() means: surrounding text, whitespace, punctuation, and ordering of non-PII tokens are unchanged. Only matched substrings are replaced. The substitution token [REDACTED-<TYPE>] is shorter than most matched substrings, so output is generally shorter than input — but no whole-line normalisation or trimming happens. This matches the CDSCO-RegAI source contract (where the logger's _redact_pii preserves the surrounding log-line shape).

Security & Compliance

  • Compliance mode: on_prem_preferred. This task introduces zero external AI / cloud API calls. Presidio runs locally; the spaCy model runs locally; no network reachability is required at runtime. build_engine() takes a NlpEngine | None — when None, Presidio constructs its default in-process spaCy engine. No HTTP client, no environment-variable reads, no os.environ access inside packages/python-core/.
  • PII handling discipline. All fixture data under tests/fixtures/india.py is synthetic — no real Aadhaar, PAN, ABHA, IFSC, voter ID, GSTIN, or medical registration numbers (per AGENT_RULES.md § Code conventions + stack.md § Test fixtures). The fixture file gets a module-level docstring explicitly stating "synthetic only — never copy from real documents". Code review check: any 12-digit number in fixture data must not pass the Verhoeff checksum (the Aadhaar validation algorithm) — the easiest way to ensure this is to use the canonical test pattern 1234-5678-9123 documented by UIDAI as invalid.
  • No PII in logs. redact() and the recogniser code do not log input strings (those are PII by definition). If diagnostic logging is added later, it routes through biltiq_privacy.core.log_filter.RedactionFilter (stack.md). For BILTIQ-002, neither module emits log records — they are pure data + pure functions.
  • No secrets. No HMAC keys, no API tokens, no env reads. The pseudonymisation surface that needs HMAC keys lives in core/pseudonymiser.py (later task), not here.
  • Library/server boundary. packages/python-core/ only — no FastAPI / Starlette / uvicorn imports. scripts/check-boundaries.sh (BILTIQ-001) catches any accident in CI.
  • License hygiene. SPDX header on every new .py file. All deps (Presidio, spaCy) are MIT / Apache-2.0; no GPL contamination risk. Per approved-versions.md: python-Levenshtein (GPL) and pymupdf (AGPL) banned — neither is touched here.
  • No ADR required. This task introduces no new AI dependency, no new external service, no new schema, no compliance-mode override, no web-framework import. The chosen approach uses Presidio's PatternRecognizer (already pinned in pyproject.toml and listed under approved-versions.md § Presidio). Spec open-question §1 ("Build cannot start until PR #1 merges") is a process gate, not an ADR.

Performance Considerations

Two distinct latency budgets, one per import path:

  • Hot path — from biltiq_privacy.indian.patterns import redact. Import cost: ~5–15 ms (Python bytecode load + 8 × re.compile). Per-call cost: O(n × p) where n = input length in bytes, p = 8 patterns. Each re.sub is C-implemented in CPython's _sre; for typical CDSCO-RegAI log lines (~200 chars) the budget is well under 100 µs per redact() call. AC5 guarantees no Presidio / spaCy import overhead bleeds in.
  • Heavy path — from biltiq_privacy.indian.recognisers import build_engine. Import cost: ~50–200 ms (Presidio's AnalyzerEngine module imports + 8 × PatternRecognizer.__init__). build_engine() call cost: ~2–4 s cold (Presidio loads spaCy en_core_web_sm model on first engine construction; matches overview.md § Data flow cold-start budget). Per-detection cost: ~10–40 ms per kilobyte of text (overview.md § Data flow). Consumers cache the engine — the spec explicitly bans a module-global singleton (spec § Out of Scope §1) so the caller owns the lifecycle.
  • Compilation at module load. The PATTERNS dict comprehension runs eight re.compile calls at patterns.py import time. Each pattern is small (< 100 chars source); compile cost is ~0.5–1 ms per pattern. Done once per process; never on the hot path. Alternative (lazy compile inside redact()) rejected — costs a per-call branch for no measurable win at typical workloads.
  • Test-suite cost. 40+ parametrised tests through redact(): ~100 ms total. 8+ engine-backed tests through build_engine(): ~3–5 s total (cold-load amortised across tests if engine is reused via the presidio_engine_indian fixture). Lazy-import subprocess test: ~150–300 ms (subprocess startup dominates). Whole module under 5 s wall-clock; comfortably inside CI budget.

Rollout Plan

Single PR, multiple atomic commits. The two modules and their tests are tightly coupled (AC3's invariant test is cross-module; AC5's lazy-import test depends on the patterns module landing first). Splitting into separate PRs would leave intermediate states with red CI. Inside the PR, plan.html will land 4–6 atomic commits — patterns first, then recognisers, then tests, then docs deltas, then CHANGELOG. Exact split is plan.html's job.

  1. Branch posture. Already on feature/biltiq-002-pii-patterns, rebased onto current main. plan.html will be written on this branch.
  2. Land code + tests + docs in one PR. Patterns module first (no dependencies); recognisers module second (depends on patterns); fixtures + parametrised tests third; invariant + lazy-import tests fourth; overview.md + stack.md + CHANGELOG deltas fifth. Each commit message follows BILTIQ-002: <step description> per AGENT_RULES.md § Working pattern rule 4.
  3. Local gate before push: ruff check packages/python-core, mypy --strict packages/python-core, pytest packages/python-core/tests/, bash scripts/check-boundaries.sh. All four green on Python 3.12 (dev default).
  4. CI gate: .github/workflows/ci.yml matrix-build on Python 3.11/3.12/3.13/3.14 × pip|uv (8 combos per BILTIQ-001 final state). Boundary check + banned-vocab + on-prem-compliance jobs from biltiq-gates.yml run alongside. AC8 explicitly demands the full matrix passes.
  5. Merge once green. No release tag — v0.1.0 PyPI publish is a separate ship task per BILTIQ-001 § Rollout.

Rollback

Pure additive Python code under a new sub-package. Rollback is git revert <merge-sha> — no data migrations, no schema state, no external service contracts to unwind. No consumer has imported biltiq_privacy.indian.* yet (CDSCO-RegAI migration is a separate repo task per spec § Out of Scope §6). The only state revert leaves behind is a contributor virtualenv with the editable install still resolving the (now-removed) indian/ path — auto-fixes on next pip install -e or uv sync.
