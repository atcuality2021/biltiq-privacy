Problem

biltiq-privacy v0.1.0’s differentiator is the Indian-context PII recogniser set (Aadhaar, PAN, ABHA, GSTIN, Voter ID, IFSC, Phone, Medical Registration). These regexes currently live inside CDSCO-RegAI in two coupled source files: backend/utils/pii_patterns.py (pure-re, used by the logger for DPDP-§4 redaction — hot path) and backend/modules/anonymisation/presidio_engine.py (Presidio PatternRecognizer + spaCy AnalyzerEngine singleton — heavy path). Both contain framework glue (CDSCO module layout, vLLM-adjacent settings, a module-global _engine) that disqualifies them as library code. Without this port, every BiltIQ consumer (CDSCO-RegAI v2, ManthanQuant, ATC CommandCenter) reimplements the same eight regexes — with drift risk and no shared test surface.

User Impact

After this ships, a downstream consumer writes from biltiq_privacy.indian.patterns import redact (zero-cost regex hot path — no Presidio, no spaCy import) or from biltiq_privacy.indian.recognisers import INDIAN_RECOGNISERS, build_engine (heavy NLP-context path) and gets the eight India-context recognisers as a tested, typed, framework-free dependency. CDSCO-RegAI’s backend/utils/log.py can drop its inline _redact_pii import and use biltiq_privacy.indian.patterns.redact verbatim. The library’s “Indian PII out-of-the-box” promise becomes real.

Acceptance Criteria

  • OPEN AC1 — biltiq_privacy/indian/patterns.py exports eight named regex constants (AADHAAR_PATTERN, PAN_PATTERN, ABHA_PATTERN, GSTIN_PATTERN, VOTER_ID_PATTERN, IFSC_PATTERN, PHONE_IN_PATTERN, MEDICAL_REG_PATTERN) as str values, a PATTERNS: dict[str, re.Pattern[str]] mapping of entity-name → compiled pattern, and a redact(text: str) -> str function that returns [REDACTED-<TYPE>] for each match.
  • OPEN AC2 — biltiq_privacy/indian/recognisers.py exports eight presidio_analyzer.PatternRecognizer objects with entity types IN_AADHAAR, IN_PAN, IN_ABHA, IN_GSTIN, IN_VOTER_ID, IN_IFSC, IN_PHONE, IN_MEDICAL_REG; an INDIAN_RECOGNISERS list constant; and a build_engine(nlp_engine=None) -> AnalyzerEngine factory that registers them. No module-global engine singleton.
  • OPEN AC3 — recognisers.py consumes regex strings from patterns.py (no string duplication). Invariant test: _GSTIN.patterns[0].regex == GSTIN_PATTERN (and equivalent for all eight).
  • OPEN AC4 — redact() preserves ABHA-before-AADHAAR ordering. Input "12-3456-7890-1234" redacts to "[REDACTED-ABHA]", not "[REDACTED-AADHAAR]". Verified by an explicit ordering test.
  • OPEN AC5 — Importing biltiq_privacy.indian.patterns does not transitively import presidio_analyzer or spacy. Verified by a test that asserts "presidio_analyzer" not in sys.modules after a fresh import of patterns in a subprocess.
  • OPEN AC6 — Test surface has ≥32 fixture cases (3–5 per pattern), covering: positive, negative, known false-positive (e.g., 12-digit non-Aadhaar invoice number, 3-letter-7-digit non-Voter-ID order code), boundary (start-of-string, embedded in URL), and the cross-pattern ABHA-before-AADHAAR invariant. Total ≥40 test cases counting invariants.
  • OPEN AC7 — mypy --strict passes on both files. No Any, no # type: ignore without an inline justification.
  • OPEN AC8 — CI matrix (Python 3.11–3.14 × pip | uv) passes for the new files. presidio-analyzer>=2.2,<3 and presidio-anonymizer>=2.2,<3 already in packages/python-core/pyproject.toml (added in BILTIQ-001).
  • OPEN AC9 — CHANGELOG.md [Unreleased] gains a line: - feat: India PII recognisers — patterns + Presidio surfaces (BILTIQ-002).
  • OPEN AC10 — No Anti-Pattern #7 residue (*_v2.*, *_new.*, *_old.*, *.bak, test_scratch_*). No banned vocabulary in code, comments, docstrings, or commit messages.
  • OPEN AC11 — Both files carry module-level docstrings naming source files (CDSCO-RegAI:backend/utils/pii_patterns.py, CDSCO-RegAI:backend/modules/anonymisation/presidio_engine.py) and the BILTIQ-002 task ID for provenance.

Out of Scope

  • The _engine module-global singleton pattern from CDSCO’s presidio_engine.py. build_engine() is a pure factory; consumers manage singleton lifecycle in their own app code.
  • The detect_pii_rules() helper from CDSCO — deferred to a later task that defines the canonical detection-result schema (currently a bespoke dict shape: {entity_type, start, end, score, text, source}).
  • EU/US recognisers (GDPR/HIPAA/CCPA entities like SSN, NHS Number, EU passport, IBAN). Separate task, separate module (biltiq_privacy/eu/, biltiq_privacy/us/).
  • Anonymisation primitives beyond redact() (k-anonymity, pseudonymisation, age encryption, format-preserving encryption). Separate tasks.
  • Custom user-supplied regex patterns at runtime — v0.2.0+.
  • Updating CDSCO-RegAI to consume biltiq_privacy. That migration is a CDSCO repo task, not a biltiq-privacy task.
  • Med Reg confidence tuning. Ships at 0.6 to match CDSCO prod; consumers can re-register a custom recogniser with a different score.
