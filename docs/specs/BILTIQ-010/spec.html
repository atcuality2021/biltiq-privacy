Problem

The engine must emit a tamper-evident audit trail. CDSCO's backend/modules/audit.py (305 LOC) does this but is heavily coupled to SQLAlchemy — it writes hash-chained rows to a DB via an async session. Only the hash-chain algorithm (~50 LOC) belongs in a leaf library; persistence is the consumer's concern. This task extracts the pure logic into core/audit_chain.py: compute chained rows and verify integrity, with a documented persistence interface — no DB in the wheel.

User Impact

Internal/infra. Consumers (CDSCO, CommandCenter) get a portable, regulator-friendly tamper-evident chain (21 CFR Part 11 / Annex 11 spirit) without inheriting a DB schema — they persist rows however they like. Feeds BILTIQ-011 (audit-trail check) and BILTIQ-012 (each anonymise call emits a row).

Acceptance Criteria

  • OPENAC1 — core/audit_chain.py exposes a pure way to append an event to a chain: given prev_hash + event fields, produce a row whose hash commits to (prev_hash, payload).
  • OPENAC2 — verify_chain(rows) -> report returns valid/invalid and the first broken index; altering any field of any row fails verification (tamper-evident).
  • OPENAC3 — No SQLAlchemy/DB/session/FastAPI imports. Persistence is documented as a consumer-supplied interface; the library never writes storage.
  • OPENAC4 — Hashing is deterministic with a documented, canonical row schema + serialization (stable key order) so chains verify across machines/languages.
  • OPENAC5 — Tests: build a multi-row chain, verify it passes; mutate a middle row, verify it is detected at the right index; empty-chain + single-row edge cases.

Out of Scope

  • DB persistence, API request logging, audit stats endpoints — stay in the consumer (CDSCO keeps its SQLAlchemy writer).
  • The 21 CFR / Annex 11 mapping document (optional later doc task).
  • Signing with asymmetric keys (follow-up if a consumer needs non-repudiation).

Open Questions

  • Timestamp source — caller-supplied vs library utcnow()? Caller-supplied keeps it pure + testable; confirm.
  • Canonical serialization — JSON with sorted keys vs a fixed field concatenation? Decide in design for cross-language verifiability.
