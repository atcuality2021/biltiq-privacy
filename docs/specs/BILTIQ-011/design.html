Task ID
BILTIQ-011
Author

Approach

Name

Frozen-dataclass report contract behind a minimal Regime ABC: regime-agnostic Regime / ComplianceCheck / ComplianceReport in regimes/base.py; all eight CDSCO checks as private methods on DPDPRegime in regimes/dpdp.py, with India-specific metadata (check IDs, legal sections, framework names, residual-pattern table, marker defaults) held as module-level data.

Description

CDSCO's backend/compliance/dpdp_validator.py (151 LOC) returns nested plain dicts from one function. This port splits it along the seam the spec names: the shape of an attestation (any regime → a report of typed checks) goes into regimes/base.py, and the eight DPDP/NDHM/ICMR check behaviours go into regimes/dpdp.py. The report types are @dataclass(slots=True, frozen=True) — mandated by approved-versions.md ("Default shape for ComplianceCheck, ComplianceReport, detector results") — with check status typed as Literal["pass", "fail", "warning", "info"] (the four statuses the source emits; no Any, Anti-Pattern #4). Overall compliant keeps the source semantic: every check must be "pass" — warning/info count against compliance, exactly as passed == total did in the source.

validate() signature. The ABC fixes validate(original, anonymised, detections, audit_records, *, generated_at) -> ComplianceReport. The four positional parameters are the spec AC2 contract; detections/audit_records reuse the shipped BILTIQ-007 Detection/AuditRecord TypedDicts from core/pseudonymiser.py (typed as Sequence[...]; a BILTIQ-009 DetectedEntity is a Detection at runtime, so detector output flows in unchanged — no parallel type, Anti-Pattern #1). generated_at: str is required, keyword-only, caller-supplied per the dev ruling and the BILTIQ-010 determinism precedent: the module never reads the clock, so identical inputs always produce an identical (and ==-comparable, thanks to frozen dataclasses) report. This is a deliberate delta from the source's datetime.now(timezone.utc).isoformat(); consumers that want a wall-clock stamp pass datetime.now(timezone.utc).isoformat() themselves (the approved-versions.md form), e.g. the BILTIQ-013 sidecar.

Configurable generalisation markers (DPDP-4 ruling, extended at design review). The marker list is a keyword-only constructor parameter — DPDPRegime(*, generalisation_markers: tuple[str, ...] = ("XXXX", "Healthcare Facility", "India")) — mirroring the PresidioDetector(*, score_threshold=0.5) constructor-injection precedent. Defaults reproduce the CDSCO trio, so default behaviour is source-equivalent while non-healthcare consumers can substitute their own markers (AC4). Per the design-review ruling (2026-06-11) the same injected marker list also drives DPDP-1's residual mask filter: a residual match is skipped when its value contains any configured marker. A consumer overriding the markers changes DPDP-1 and DPDP-4 consistently (one notion of "what generalised output looks like"). There is no separate _MASK_MARKER constant. This widens the source's filter (which skipped only "XXXX"-containing values) to all three default markers — behaviour delta (d), ratified at plan review: a residual value containing a descriptive marker (e.g. a leaked email such as contact@AirIndia.com, whose text contains "India") is filtered here but would have been flagged by CDSCO — a known false-negative surface in the default configuration, accepted for marker-semantics consistency and pinned by a dedicated test so the behaviour is visible, not accidental. Consumers wanting source-strict DPDP-1 filtering pass generalisation_markers=("XXXX",).

Checks as methods, metadata as data (not a data-driven check registry). Each check is a private method (_check_pii_removal, _check_audit_trail, … _check_icmr_ethics) returning one ComplianceCheck; validate() calls them in the fixed source order and assembles the report. The eight checks take heterogeneous inputs (text scan; two list-length comparisons; a token-shape probe; a substring scan; a set intersection; a length ratio) — a generic predicate table would force a one-size (context: dict[str, object]) -> bool signature that erodes mypy --strict typing for zero extensibility gain. What AC4 actually requires — that CDSCO/NDHM/ICMR references be data, not behaviour baked into the abstraction — is satisfied by keeping base.py entirely regime-agnostic and holding all India-specific identity as data in dpdp.py: check IDs in legal-section format (DPDP-1…DPDP-6, NDHM-1, ICMR-1), section strings, frameworks = ("DPDP Act 2023", "NDHM", "ICMR", "CDSCO") as a ClassVar, the residual-pattern table, and the marker defaults. NDHM-1 and ICMR-1 stay in dpdp.py per the dev ruling (India-specific frameworks).

Residual scan: reuse BILTIQ-002 + port only EMAIL (AC3 ruling). The DPDP-1 scan iterates a module-level _RESIDUAL_PATTERNS: Final[dict[str, re.Pattern[str]]] built as {**PATTERNS, "EMAIL": re.compile(EMAIL_PATTERN)} — the eight compiled BILTIQ-002 patterns by reference (never re-declared) plus the single pattern 002 lacks, EMAIL, ported verbatim from CDSCO's pii_patterns.py (\b[\w.+-]+@[\w-]+\.[\w.]+\b) as a Final[str] in dpdp.py (placement weighed in § Alternatives). The scan ports the source's two token-skip heuristics verbatim (skip a match directly preceded by _; skip a match inside an unclosed [ bracket — both protect pseudonym tokens like [IN_AADHAAR_1a2b3c4d]) and the "XXXX" mask filter. Three behaviour deltas vs the source, all pinned by tests: (a) stricter scan — CDSCO scanned 5 types (ABHA, AADHAAR, PAN, PHONE, EMAIL); we scan 9, so residual GSTIN / Voter ID / IFSC / Medical-Reg values now fail DPDP-1; (b) phone boundary — BILTIQ-002's PHONE_IN_PATTERN uses \b where the source used an underscore-permitting lookbehind, changing matching adjacent to underscores (e.g. patient_98765…pdf filenames); (c) no PII values in the report by default — evidence is carried as "TYPE@position" strings (e.g. "AADHAAR@112") rather than the matched text, where the source embedded the leaked value itself. The report is exactly the artifact consumers persist, log, and (BILTIQ-013) return over HTTP; copying leaked PII into it would re-leak what the check exists to catch. Per the design-review ruling (2026-06-11) this is configurable: DPDPRegime(*, include_values: bool = False) — when True, evidence strings carry the matched value ("AADHAAR@112:1234 5678 9012", source-equivalent triage detail) for consumers whose report sink is access-controlled. The safe behaviour is the default; the flag's docstring warns that enabling it places PII in the report. A fourth delta, (d) wider mask filter — DPDP-1's residual filter skips matches containing any configured marker, not only "XXXX" (see the marker paragraph above; ratified at plan review, pinned by test). Evidence is capped at 5 entries, porting the source's real_residual[:5]; details carries the full count.

DPDP-5 coverage set. The Indian-type set is a module constant _INDIAN_ENTITY_TYPES: Final[frozenset[str]] listing the eight IN_* entity names exactly as indian/recognisers.py declares them (IN_AADHAAR, IN_PAN, IN_ABHA, IN_GSTIN, IN_VOTER_ID, IN_IFSC, IN_PHONE, IN_MEDICAL_REG) — identical to the source's set. It cannot be derived mechanically from PATTERNS keys (the PHONE_IN key maps to the IN_PHONE entity), so a consistency test asserts the constant equals the recognisers' supported_entity set, preventing silent drift.

Data Model Changes

Three new in-library types in regimes/base.py; no DB table, no JSONL field, no schema migration, no change to shipped types.

# regimes/base.py
from __future__ import annotations
from dataclasses import dataclass
from typing import Literal, TypeAlias

CheckStatus: TypeAlias = Literal["pass", "fail", "warning", "info"]   # the 4 source statuses

@dataclass(slots=True, frozen=True)
class ComplianceCheck:
    check_id: str                    # legal-section ID: "DPDP-1" .. "DPDP-6", "NDHM-1", "ICMR-1"
    name: str                        # source "check" field, e.g. "PII Removal Completeness"
    description: str                 # source description, verbatim
    status: CheckStatus
    details: str                     # human-readable outcome line (counts, never PII values)
    section: str                     # legal citation, e.g. "Section 8(1) — Data Minimisation"
    evidence: tuple[str, ...] = ()   # "TYPE@position" locators (default); values appended only on include_values=True (delta c); capped at 5 entries, ported from the source's real_residual[:5]

@dataclass(slots=True, frozen=True)
class ComplianceReport:
    regime_id: str                   # e.g. "DPDP-2023"
    compliant: bool                  # all checks status == "pass" (source: passed == total)
    passed: int
    total: int
    checks: tuple[ComplianceCheck, ...]   # fixed source order; tuple keeps the dataclass hashable-safe
    generated_at: str                # caller-supplied, echoed verbatim — no clock read
    frameworks: tuple[str, ...]      # ("DPDP Act 2023", "NDHM", "ICMR", "CDSCO") for DPDP

    @property
    def score(self) -> str:          # source "score" field, derived: "7/8"
        return f"{self.passed}/{self.total}"

Field renames from the source dict (id → check_id, check → name, dpdp_compliant → compliant, residual → evidence) avoid a builtin shadow and de-Indianise the base contract; the BILTIQ-013 sidecar owns any wire-format naming. The BILTIQ-007 Detection/AuditRecord TypedDicts are consumed, not modified.

Security & Compliance

  • Compliance mode on_prem_preferred — unaffected. The module is pure stdlib (abc, dataclasses, re, typing) plus in-repo imports (indian.patterns, core.pseudonymiser types). No network, no external/cloud AI, no new dependency → no ADR required: no dependency is added, no schema changes, no external service is integrated, and the design follows the established BILTIQ-009/010 porting pattern. (We concur with the Step-1 assessment; the plan-reviewer can challenge.)
  • No PII in the report or logs by default. The module performs no logging at all (no logging call, no print()); the returned report carries counts, statuses, and "TYPE@position" locators — never matched text, original text, or detection values (delta c, § Approach). details strings are count-only by construction. The sole exception is the explicit include_values=True opt-in (dev-ratified), whose docstring warns that the report then contains PII and must go only to access-controlled sinks; the default is always safe.
  • Library/server boundary: no FastAPI/Starlette/uvicorn/pydantic/DB import anywhere in regimes/ (AC4); the test_lazy_import.py subprocess probe enforces it structurally, satisfying the code-review auto-block.
  • No secrets, no env reads: the regime takes no key and reads no environment (AGENT_RULES.md secrets rule); the only configuration is the marker tuple, injected at construction.
  • Tests use synthetic PII only — values from the BILTIQ-002 *_VALID tuples / tests/fixtures/india.py; no real identifiers anywhere, including in the delta-pin cases.
  • Honest attestation scope: the report attests the eight ported checks against DPDP 2023 / NDHM / ICMR references; it is not a certification claim (AGENT_RULES.md § Banned in product specs). Docstrings state this plainly.

Performance Considerations

The hot path is DPDP-1's residual scan: nine pre-compiled finditer passes over the anonymised text — O(9·n) with small constants. All nine patterns are simple bounded-quantifier character-class regexes (no nested quantifiers, no alternation explosion), so there is no catastrophic-backtracking surface; a 1 MB document costs nine linear scans, low tens of milliseconds on commodity hardware. The per-match skip heuristics slice two short fixed-width windows (≤ 20 chars) — O(1) per match. Eight of the nine compiled patterns are shared with BILTIQ-002 (compiled once at indian.patterns import); only EMAIL compiles at dpdp.py import. The remaining checks are trivial: DPDP-4 is k substring searches (k = 3 by default, O(k·n)); DPDP-2/3/5/NDHM-1 are O(d) passes over detections/audit records; DPDP-6 is O(1) arithmetic. No model load, no NER, no I/O — importing and running the regime never touches Presidio/spaCy. validate() makes a single pass over each input; nothing is re-scanned. No latency-budget concern for the sidecar's per-request path (BILTIQ-013).
