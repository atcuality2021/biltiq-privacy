Problem

The engine must attest anonymised output against a regulatory regime, not just transform it. CDSCO's backend/compliance/dpdp_validator.py (151 LOC) runs 8 checks (residual-PII scan, audit trail present, token reversibility, generalisation irreversibility, Indian-PII coverage, data minimisation, NDHM, ICMR) using pii_patterns. Port it behind a generic Regime abstraction so GDPR/HIPAA/CCPA (Phase C) slot in later, and so consumers get a structured ComplianceReport.

User Impact

Internal/infra → external attestation. Consumers can call one regime and get a pass/fail ComplianceReport with per-check results — the feature that distinguishes biltiq-privacy from a plain redaction library. First regime: DPDP 2023 (India).

Acceptance Criteria

  • OPENAC1 — regimes/base.py defines a Regime ABC plus ComplianceCheck and ComplianceReport dataclasses (typed, no Any).
  • OPENAC2 — regimes/dpdp.py implements all 8 CDSCO checks via validate(original, anonymised, detections, audit_records) -> ComplianceReport, behaviour-equivalent to the source.
  • OPENAC3 — Residual-PII scan reuses shared patterns; Indian patterns reuse BILTIQ-002 rather than redefining (port only what 002 lacks, e.g. EMAIL).
  • OPENAC4 — Pure: no FastAPI/DB. CDSCO/NDHM/ICMR framework references are data/config, not hardcoded behaviour that blocks reuse.
  • OPENAC5 — Tests: each of the 8 checks has a passing and a failing case where the source defines one (e.g. residual Aadhaar → fail; clean text → pass). DPDP-6 and ICMR-1 are hardcoded always-pass in the CDSCO source — they get always-pass + edge-case tests instead of invented fail paths (annotation ratified 2026-06-11 at plan review; inventing fail paths would break AC2 equivalence).

Out of Scope

  • GDPR / HIPAA / CCPA regimes (BILTIQ-017/018/019).
  • responsible_ai (fairness, model cards, transparency) — CDSCO-specific; deferred / may be dropped.
  • HTTP exposure of the report (BILTIQ-013).

Open Questions — all resolved 2026-06-11 (Step 1 Think, dev rulings)

  • High-risk? Yes — compliance attestation. Human plan-review is mandatory before Build (spec header already allocates 30 min).
  • NDHM/ICMR placement: stay in dpdp.py as data-driven check definitions (both are India-specific frameworks); base.py stays regime-agnostic. Plan-reviewer may challenge.
  • Report timestamp (ruling): caller-supplied, per the BILTIQ-010 determinism precedent — no clock read inside the library. Deliberate delta from the CDSCO source's datetime.now(timezone.utc).
  • AC2 vs AC3 precedence (ruling): AC3 wins. Residual scan reuses BILTIQ-002's 8 compiled patterns plus a newly ported EMAIL pattern. Two documented behaviour deltas vs source: (a) scan covers 4 extra Indian types (stricter), (b) BILTIQ-002's phone regex uses \b instead of the source's underscore-permitting lookbehind (laxer on patient_98765…pdf filenames). Both deltas must appear in design.html and be pinned by tests.
  • DPDP-4 generalisation markers (ruling): configurable marker list parameter defaulting to the CDSCO trio ("XXXX", "Healthcare Facility", "India") — behaviour-equivalent by default, reusable per AC4. Extended at design review: the same injected list also drives DPDP-1's residual mask filter (no separate fixed constant).
  • PII values in report evidence (design-review ruling): configurable — include_values: bool = False; DPDP-1 evidence carries "TYPE@position" locators by default, matched values only on explicit opt-in. Documented behaviour delta (c) vs the source, which embedded values unconditionally. Evidence capped at 5 entries (source's [:5] ported).
  • DPDP-1 marker filter width (plan-review re-ruling): the shared marker list filters DPDP-1 residuals on all configured markers, not only "XXXX" — documented behaviour delta (d) with a known false-negative surface in the default config (descriptive markers like "India" can mask a leaked value containing them), accepted for marker-semantics consistency, pinned by test; generalisation_markers=("XXXX",) is the source-strict escape hatch.
