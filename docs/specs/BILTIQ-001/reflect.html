What Went Well

  • Parallel-subagent Step 4 review caught 3 doc-sync issues the in-line build missed. Five reviewers ran independently against logical slices (engine / sidecar / root / CI+scripts / docs) and the four code slices came back clean while the docs slice found a stale ADR install-shape, an under-counted Files-to-Touch inventory, and an AC10 wording / implementation drift. Inline review wouldn't have flagged any of these — they're cross-file consistency issues that need a reader who hasn't internalised the build's running narrative. Pattern to repeat for any PR >10 files.
  • Step 3 verification caught the ${PROJECT_ROOT} resolver drift one step before the canonical install path landed. Design.html named biltiq-privacy @ file://${PROJECT_ROOT}/../python-core as the transitional path; the per-step verification gate (4-version smoke) revealed uv interprets ${PROJECT_ROOT} as the workspace root (not per-package dir). Fix landed at Step 3, not Step 4 where it would have compounded with the pip-vs-uv install-path divergence. Per-step gates earn their token cost in moments like this.
  • Two install paths verified by an 8-combo gate at Step 4, not deferred to "we'll see what CI says". pip × {3.11, 3.12, 3.13, 3.14} + uv × {3.11, 3.12, 3.13, 3.14}, all 8 green locally before any push. CI on PR #1 confirmed in 55s. The 8-combo gate took ~15 min of wall-clock and surfaced the uv-3.14-spaCy-wheel-gap (Risk #1 second firing) that GitHub Actions on pip-only would never have seen.
  • Documenting transient resolver constraints with a concrete removal trigger. The spacy<3.8.14 uv constraint is in a dedicated § Transient resolver constraints table in approved-versions.md with a column "Remove when" — not a buried comment, not an indefinite pin. When the next spaCy release ships cp314 wheels, the constraint comes out with a one-line PR.
  • BILTIQ-000 hotfix bundled as a carved-out commit, not folded into a BILTIQ-001 step. When biltiq-gates.yml's YAML-comment-in-job-name bug surfaced post-Step-6, the fix went on the same branch but as separate commits (adf0b28, 0edaca5) with BILTIQ-000 hotfix: message prefix. PR description names it explicitly. Keeps the BILTIQ-001 narrative atomic without forcing a second PR cycle.

Process Changes Proposed

  • /biltiq-engineering:build should require reflect.html to be filled (not just present) before declaring the task done. The current Build skill's plan-driven step 7 ("update README") was the last shipped commit, but the Attack Loop's seventh canonical step is Reflect. Today reflect.html exists as a template file in the diff (good — proves it was added during the task) but the build agent did not write actual content into it. Suggestion: extend the Build skill's per-step gate to include "if this is the last plan step, also write reflect.html with substantive content" — or have /biltiq-engineering:reflect auto-run at end-of-build. Caught by review skill F1, which is the correct fall-back but a costly round-trip.
  • Build skill should run a final "design ↔ diff inventory" check before completion. F2 (Files-to-Touch under-counted by 3 docs deltas) was a mechanical reconciliation issue — comparing git diff --name-only main...HEAD against design.html's enumerated file list. Could be a one-step shell-callable check that fails the build if the diff contains files not in the inventory (with an explicit "documentation-only deltas are OK if recorded under § Documentation deltas" carve-out). Saves a review round-trip on every multi-step task.
  • plan-reviewer (or a new lint) should flag YAML name: fields containing unquoted #. The biltiq-gates.yml bug was YAML correctly parsing name: Anti-Pattern #7 — ... as name: Anti-Pattern (rest stripped as comment). GitHub Actions' validator silently rejects the result. A repo-level pre-commit hook running yamllint with the truthy/comments-indentation rules plus a custom rule for "name field truncated by inline #" would catch this category. Worth a small follow-up task to add to the BiltIQ template's .pre-commit-config.yaml.
  • Reviewer slice protocol: per-slice constraint lists should be generated, not hand-written. The 5 reviewer prompts in this Step 4 review each had a slice-specific constraint section pasted in by the dispatcher. Worked fine, but is reusable scaffolding — a slice-spec file (docs/architecture/review-slices.yaml) could declare slice membership + per-slice critical-constraint anchors, and the review skill could compose prompts deterministically. Out of BILTIQ-001 scope; flagging for the engineering plugin roadmap.
