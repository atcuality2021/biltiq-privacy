Approach

Name

Hatchling-built monorepo with a dual install path (pip canonical, uv opt-in) and a grep-based boundary guard.

Description

Two independent pyproject.toml files under packages/python-core/ and packages/python-server/, both using hatchling as the PEP 517 build backend (per docs/architecture/approved-versions.md and BILTIQ-000 decision §6 monorepo, §8 fork policy). A third pyproject.toml at the repo root is a real installable metapackage (name = "biltiq-privacy-workspace", version = "0.1.0", hatchling backend, not published to PyPI) whose [project.dependencies] are two path references — biltiq-privacy @ file://packages/python-core and biltiq-privacy-server @ file://packages/python-server. Running pip install -e . at the repo root resolves both, installing them editably with the server picking up the local core sibling. This satisfies AC10 without uv. The same root pyproject.toml additionally carries a [tool.uv.workspace] declaration so contributors who prefer uv sync (faster, lockfile-aware) get the same result via the opt-in path. Each package's own pyproject.toml remains the sole source of truth for its PyPI metadata; downstream consumers continue to see two clean, independently-versioned distributions.

The library/server boundary (AC9) is enforced by a 20-line POSIX shell script scripts/check-boundaries.sh that greps every .py file under packages/python-core/ for forbidden imports (fastapi, starlette, uvicorn) and exits non-zero on hit. CI invokes it once per workflow run (not per matrix cell) as a dedicated job. A new .github/workflows/ci.yml runs the Python 3.11/3.12/3.13/3.14 install + lint + mypy + import-test matrix; it is additive to the existing biltiq-gates.yml (which keeps doing residue / banned-vocab / on-prem compliance scans).

Trade-off accepted: the root metapackage adds one file's worth of maintenance (two path-dep entries to keep in sync with package names). uv is introduced as an opt-in contributor tool — not pinned into wheels, not required for CI, but documented in README.md as the recommended fast path. Both paths are first-class supported. This is a new tooling posture not listed in the BILTIQ-000 decisions, so an ADR is required before merge (see § ADRs needed).

Alternatives Considered

Workspace pattern (chosen: hatchling metapackage at root + opt-in uv workspace declaration)

#AlternativeWhy Rejected / Chosen
1Hatch native workspaces ([tool.hatch.envs.*] across packages)Hatch's multi-package environment feature is built around shared envs for a single project, not cross-package editable installs; getting biltiq-privacy-server to pick up an editable biltiq-privacy sibling requires custom scripts and is brittle on first-time-contributor setup. Fails the AC10 "one command" smell test.
2Poetry workspaces (path deps + [tool.poetry.group])Forces poetry as the project's lockfile/install tool, which conflicts with the published-via-hatch-build-backend posture and adds a heavyweight dep most consumers won't need. BILTIQ-000 decision §6 implies one backend; mixing Poetry as orchestrator is needless surface area.
3No workspace — each package independent, contributors run pip install -e twiceWorks correctly but fails AC10 ("one command at repo root"). Also makes the server's dependency on the local core fragile — by default pip install -e packages/python-server resolves biltiq-privacy from PyPI (which doesn't exist yet at v0.1.0), not from the sibling source tree.
4uv workspaces only (uv is the sole supported install path)Faster and cleaner for uv users, but mandates uv as a contributor dependency. Subagent's first recommendation; rejected by dev on 2026-05-17 in favor of broader compatibility — internal BiltIQ engineers and external OSS contributors should not have to install a second toolchain.
5 ✓Hatchling metapackage at root + [tool.uv.workspace] alongside it (chosen)Root pyproject.toml is a real installable distribution (not published) with two path-dep entries; pip install -e . at root installs both packages editably. The same file also carries a [tool.uv.workspace] table so contributors who prefer uv get the fast path (uv sync ≈ 60s vs pip ≈ 90s on warm cache). Both paths are first-class. Adds ~10 lines of TOML maintenance vs option 4 in exchange for AC10 compatibility without forcing a uv install on any contributor.

Library/server boundary enforcement (chosen: bash grep)

#AlternativeWhy Rejected
1 ✓POSIX scripts/check-boundaries.sh using grep -rE (chosen)Zero install footprint, runs identically on dev machine + CI + pre-push hook, ~20 lines. Spec literally names this path in AC9.
2import-linter with a .importlinter contracts fileRequires a dev dependency and a config file; equivalent enforcement but adds setup steps. Worth revisiting in v0.2.0 if the rule set grows beyond "no web frameworks in core".
3Custom Ruff plugin / per-file-ignores using flake8-import-restrictionsCustom ruff rules need a ruff-internal API that's not yet stable for plugin authors; flake8 plugin pulls in flake8 alongside ruff. Tool overlap rejected.
4CI-only check (workflow step with inline grep)Loses local-developer feedback. Spec's scripts/check-boundaries.sh path puts it at the developer's hand, not just in CI.

CI matrix shape (chosen: single workflow, 4 Python × 2 packages, boundary as a separate job)

#AlternativeWhy Rejected
1 ✓One ci.yml with matrix: { python: [3.11,3.12,3.13,3.14], package: [python-core, python-server] } (chosen)8 parallel cells, each installs one package + runs lint + mypy + import-test. A separate boundary-check job (no matrix) calls scripts/check-boundaries.sh. Total wall-clock ≈ 8 min with cache. Clean for CI dashboard reading.
2Two workflows — ci-core.yml and ci-server.ymlDoubles maintenance for no parallelism gain (GH Actions parallelises matrix cells anyway). Spec AC7 names a single ci.yml.
3Single matrix cell per Python version, running both packages serially inside one cellLoses per-package failure isolation; one failed mypy in server hides core's success. Harder to read CI output.

Boundary script location (chosen: scripts/check-boundaries.sh)

#AlternativeWhy Rejected
1 ✓scripts/check-boundaries.sh (chosen)Spec AC9 names this exact path. scripts/ is the documented location for repo-wide helpers per overview.md § Where new code goes.
2scripts/ci/check-boundaries.shImplies CI-only; the script is also useful as a developer-side pre-push manual check. Top-level scripts/ signals that.
3Inline in the workflow YAMLSplits the rule between two places (script vs CI) and loses local invocability. Already rejected in the previous table.

Security & Compliance

  • Library/server boundary as a regulatory-relevant rule. Downstream consumers running on_prem_required (CDSCO-RegAI healthcare workloads, DPDP-sensitive deployments) need to pip-install biltiq-privacy without dragging in a web framework. The boundary script (AC9) makes that contract machine-checkable from day one, before any code is ported. A future ADR override (web-framework import added to packages/python-core/) per AGENT_RULES.md § Architectural decisions stays the explicit escape hatch.
  • Pin discipline. All dependencies use upper bounds (< 3, < 4, < 1) per approved-versions.md. No * versions, no unpinned transitives, no --pre at install time. Compliance audits (Brief §2 rule 1 — no forks, vendored mirrors only) depend on this being machine-readable.
  • MIT license headers. Each new pyproject.toml declares license = { text = "MIT" }; each new Python file gets the SPDX one-liner # SPDX-License-Identifier: MIT at the top per BiltIQ convention. LICENSE at repo root already exists from BILTIQ-000.
  • No secrets in CI. The new ci.yml uses only the GitHub-managed GITHUB_TOKEN (implicitly, for checkout). No secrets.* references. No third-party API tokens needed at the scaffolding stage. When BILTIQ-002+ ports the engine, secret-handling stays a constructor-arg contract per AGENT_RULES.md § Code conventions — out of scope here.
  • No cloud AI usage. Mode is on_prem_preferred; this task introduces zero AI calls of any kind. The existing biltiq-gates.yml on-prem-compliance job will confirm.
  • Workflow security. No ${{ ... }} interpolation in run: blocks for user-controllable fields (PR title, branch name, etc.) — matrix values (Python version, package name) come from the workflow's own literal arrays, which is safe per GitHub's security guidance and matches the pattern already used in biltiq-gates.yml.

Performance Considerations

BILTIQ-001 has no runtime hot path. Performance concerns reduce to CI matrix wall-clock and contributor cold-install time:

  • CI per-cell budget. 8 matrix cells (4 Python × 2 packages) running in parallel. Per cell: Python setup (~20s), pip install with cache (~60-120s; first run ~3 min until cache is warm), ruff (<5s), mypy on near-empty package (~10s), pytest of one import test (~5s). Per cell ~3-5 min warm, ~6-8 min cold. Wall-clock end-to-end with GH Actions' default concurrency ≈ 8 min warm.
  • spaCy en-core-web-sm download. The URL-pinned dep is a ~12 MB tar.gz wheel resolved at install time (not from PyPI's index). It's the single largest contributor to cold-install time (~30-90s per cell). Mitigation: actions/setup-python's built-in pip cache keys on the pyproject + lockfile hash, so cache hits after the first PR cut this to ~2s. Document the cache key in ci.yml.
  • Contributor first-install. uv sync at repo root (or pip install -e packages/python-core packages/python-server) ≈ 60-90s on a warm pip cache, 3-5 min cold. Acceptable for a once-per-clone cost.

None of these are user-facing — engine latency budgets in overview.md § Data flow (~15-50 ms warm path) are unaffected because no engine code lands in BILTIQ-001.

Rollout Plan

Single PR, single commit. All scaffolding is interdependent: the boundary script needs the package paths to exist, the CI workflow needs the pyprojects to exist, the import tests need both. Splitting buys nothing and would leave intermediate commits with red CI. Recommendation: one commit BILTIQ-001: scaffold monorepo packages/ skeleton + CI matrix on a topic branch, PR against main, merge once green on all 4 Python versions.

  1. Branch from main as biltiq-001-skeleton.
  2. Create all files listed in § Files to Touch.
  3. Run locally on Python 3.12 (most likely dev default): uv sync, ruff check packages/, mypy --strict packages/, pytest packages/, bash scripts/check-boundaries.sh — all green.
  4. Commit, push, open PR. .github/workflows/ci.yml runs the 4 × 2 matrix + boundary check. Expect 3.14 cell to be the highest-risk; see § Risks.
  5. Merge once green. No release tag — per Out of Scope §8, v0.1.0 PyPI publish is a separate ship task.

Rollback

Pure scaffolding. Rollback is git revert <merge-sha> — no data migrations, no schema state, no external service contracts to unwind. The only "dirty" state a revert leaves behind is contributor venvs with the editable installs still resolving — those auto-fix on next uv sync or pip install -e.

#RiskSeverityDetection / Mitigation
1 spaCy / Presidio wheel availability on Python 3.14. 3.14 was released Oct 2025. presidio-analyzer 2.2.x and spacy 3.7.x historically lag a release cycle on cpython bumps. There is a non-trivial chance the 3.14 matrix cell fails at pip install with "no compatible wheel" — particularly for any binary deps (e.g. blis, thinc) in the spaCy chain. LOW (was HIGH; downgraded 2026-05-17) Original mitigation (Path A, plan-confirm): allow-prereleases: true + accept source builds. What actually happened (Step 2 verification, 2026-05-17): 3.13 install failed first — blis 0.7.11 has no cp313 wheel and gcc AVX-512 source build fails on the dev machine. Adopted mitigation (ADR-0002): bumped en-core-web-sm URL pin 3.7.1 → 3.8.0, cascading to spacy 3.8.x / thinc 8.3.x / blis 1.3.x. All four Python versions install from binary wheels; no compiler dependency on the runner. Local Step 2 gate confirmed 2/2 tests pass on 3.11, 3.12, 3.13, 3.14.
2 uv workspace + URL-pinned en-core-web-sm interaction. uv's workspace resolver interacts with hatchling's [tool.hatch.metadata.allow-direct-references] setting. Possible failure mode: uv sync at repo root rejects the direct URL ref despite the hatch allowance. Severity downgraded to LOW (2026-05-17) because uv is now opt-in, not required — if uv sync breaks, contributors fall back to pip install -e . which has different URL-pin semantics and is the canonical path. CI uses pip throughout, so this never blocks merge. LOW Detection: uv sync at repo root fails locally on Python 3.12 for any contributor exercising the opt-in uv path. Mitigation: configure [tool.uv] with allow-direct-url = true in the root pyproject.toml. AC8 scopes to the five subdirs under biltiq_privacy/; tests live at packages/python-core/tests/ (sibling of biltiq_privacy/), so they fall outside AC8. Dev confirmed the reading. ADRs Needed Before Build

The following design decisions sit outside the 10 architectural decisions taken at BILTIQ-000 and therefore need an ADR recorded under docs/adr/ before Step 3 (Build):

  • ADR-0001 (or next number): Dual contributor install paths — pip install -e . (canonical) and uv sync (opt-in fast path) — both backed by a hatchling-built root metapackage with two path-deps and a parallel [tool.uv.workspace] declaration. Documents why hatch native workspaces / Poetry / no-workspace / uv-only were rejected. Notes that uv is an opt-in developer-side tool, not a build-time or runtime dep of either published wheel, and not required for CI. Links: approved-versions.md § Hard dependency pins, BILTIQ-000 decision §6 (C-as-SDKs monorepo), conversation 2026-05-17 (dev rejected uv-only path).

No other ADRs required. The other design choices (bash boundary script, single ci.yml workflow, scripts/ path) follow existing conventions in AGENT_RULES.md and overview.md § Where new code goes.

Anti-Pattern Guardrails Honored

  • #1 Duplication — clean. The repo has no existing pyproject.toml, no packages/, no scripts/check-boundaries.sh, no .github/workflows/ci.yml. The existing biltiq-gates.yml is kept intact (its checks complement, do not overlap, the new ci.yml).
  • #2 Abstraction Bypass — clean. The stack's internal modules table lists no scaffolding-related wrappers; the chosen approach uses standard tooling (hatchling, uv, ruff, mypy, pytest) per AGENT_RULES.md § Stack.
  • #9 Deprecated API Usage — clean. __version__ uses importlib.metadata (current per approved-versions.md), not pkg_resources. No distutils, no setup.py, no datetime.utcnow().
  • #11 HTML/MD boundary — clean. This file is design.html, paired with spec.html per the convention.
