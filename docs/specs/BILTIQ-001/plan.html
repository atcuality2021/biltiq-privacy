Rollback Plan

Pure scaffolding — additive only, no data migrations, no schema state, no external service contracts to unwind. Per-step rollback is git reset --hard HEAD~1 before the next step's commit; cross-step (post-merge) rollback is git revert <merge-sha> on a follow-up PR. The only contributor-side cleanup after a revert: pip uninstall biltiq-privacy biltiq-privacy-server biltiq-privacy-workspace in any venv that ran pip install -e ., then rm -rf .venv and re-create. Auto-fixed on next uv sync or pip install -e . after the revert lands.

No production deployment risk in this task — the PyPI release is a separate ship task (per spec § Out of Scope §8). CI workflows in .github/workflows/ci.yml are sandbox-scoped to GitHub-managed GITHUB_TOKEN only; no third-party secrets touched.

R1 Python 3.14 wheel availability for spaCy / Presidio / their transitive C-extension deps. spaCy's released wheels at lock time are 3.7.x with 3.13 support; 3.14 may need a source build. Step 2, 3, 4 (local matrix); Step 6 (CI matrix) LOW (was HIGH at plan-confirm; downgraded 2026-05-17 after Step 2 verification — see ADR-0002) Original (Path A, plan-confirm): accept source builds on 3.13/3.14, escalate to dev if a binary dep fails. What actually happened: 3.13 install failed at blis 0.7.11 source build (no cp313 wheel; gcc AVX-512 compile failure). Adopted mitigation: bumped en-core-web-sm URL pin from 3.7.1 → 3.8.0 (ADR-0002), cascading to spacy 3.8.x / thinc 8.3.x / blis 1.3.x — all four Python versions install from binary wheels, no compiler dependency. Verified locally during Step 2: 2/2 tests pass on 3.11, 3.12, 3.13, 3.14.
R2 Local 4-version matrix prerequisite — dev environment must have uv 0.4+ with Pythons 3.11/3.12/3.13/3.14 installed, otherwise the per-step gates in Steps 2–4 cannot run. Step 2, 3, 4 MED Header Prerequisites box names the exact uv python install command. Documented fallback chain: uv → pyenv → "uv-only-on-3.12 + trust CI for the other three" with explicit plan amendment if invoked. Risk shifts to CI (R1) under the last fallback but does not block the plan.
R3 en-core-web-sm 3.7.1 URL pin reachability — github.com/explosion/spacy-models/releases/download/... must be reachable from CI runners and contributor machines at install time. GitHub Releases occasionally have transient outages; a stricter problem applies in airgap deployments downstream (out of scope for BILTIQ-001, but worth flagging). Step 2 (local), Step 6 (CI) LOW Hatchling's [tool.hatch.metadata.allow-direct-references] handles the URL syntax. README Step 7 documents the dependency on github.com being reachable. Wheel-vendoring for airgap installs is explicitly deferred to a later task; flag this in the BILTIQ-001 PR description so reviewers see the deferral. If CI flakes on the download, the retry is a re-run, not a code fix.
R4 pip vs uv path-source semantics divergence at the root metapackage. pip reads [project.dependencies] with file:// direct refs (via allow-direct-references); uv reads [tool.uv.sources] for workspace path overrides. The two configs must agree on which packages are local and which would resolve from PyPI — drift here would cause one toolchain to install a stale PyPI version while the other uses the local checkout. Step 4 MED The Step 4 gate explicitly requires both install paths to succeed on all 4 Python versions (8 combinations) before commit. The smoke test prints __version__ for both packages — a stale-PyPI resolution would print whatever the last published version is (currently nothing — package not yet on PyPI), making divergence loud rather than silent. As insurance, the BILTIQ-001 PR description will call out both [project.dependencies] and [tool.uv.sources] entries side by side for human review.
